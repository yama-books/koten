対象: `conj/CLAUDE_CODE_AUDIT_PROMPT_2026-09-21.md` の既知テストケース1・2。

## 重要な前置き: このデータはどこにあるか

`LOCAL_HANDOFF_2026-09-21.md` / `CLAUDE_CODE_AUDIT_PROMPT_2026-09-21.md` は
「910例の内部QAデータ」を主対象として指定しているが、**「思へらず」も「変る」
も、Google Drive の内部QA ZIP (`katsuyo_v0.4.18_internal_package_2026-09-20.zip`
内 `data/verb_examples.json` / `data/auxiliary_examples.json` 等、910例) の
中には存在しない。**

両方とも、現在 **公開中の** `conj/index.html` に埋め込まれている、別の・より
小さいデータセット（129項目: 動詞89 / 形容詞11 / 形容動詞1 / 助動詞28、
`conj/HANDOFF.md` 記載の棚卸しと一致）の中にある。

この129項目データは `const items=[...]` として `conj/index.html` に直接
埋め込まれており、スキーマも内部QA 910例とは異なる（`target` / `example`
の単純な2フィールド構造で、`anchor` / `normalizedKey` / `displayTarget` の
ような分離レイヤーが存在しない）。マーカー生成ロジックも別物:

```js
// conj/index.html
function highlight(text,target){
  if(!target)return text;
  const i=text.indexOf(target); if(i<0)return text;
  return text.slice(0,i)+"<mark>"+text.slice(i,i+target.length)+"</mark>"+text.slice(i+target.length);
}
```

（内部QA側の `highlightTarget(text,target,occurrence)` とは occurrence
引数の有無を含めて別実装。）

したがって、今回の「思へらず」「変る」調査は **公開版129項目データセット**
に対する調査であり、910例の自動監査（`marker-kana-audit-v1.csv`）とは
別ファイルとして報告する。910例側にも構造的に同種の懸念（後続助動詞への
越境）が疑われる候補が21+7=28件あるため、そちらは
`marker-kana-audit-v1.csv` の `REVIEW_MARKER` / `REVIEW_BOTH` 行を参照。

## 既知テストケース1: 「思へらず」(`ri_aux`)

`conj/index.html` 内の該当項目:

```js
{id:"ri_aux",pos:"aux",label:"助動詞",lemma:"り",kind:"ラ変型",
 forms:[F(["ら"]),F(["り"]),F(["り"]),F(["る"]),F(["れ"]),F(["れ"])],
 meaning:"完了・存続",connection:"四段已然形・サ変未然形",connectionShort:"四已・サ未",
 poem:null,source:"土佐日記",target:"らず",
 example:"舟子、かぢとりは、舟唄うたひて何とも思へらず"}
```

| 項目 | 値 |
|---|---|
| example ID | `ri_aux` |
| 品詞 | 助動詞 |
| 問われている活用語 | 助動詞「り」（ラ変型: ら／り／り／る／れ／れ） |
| raw target（データ上） | `らず` |
| 期待されるtarget | `ら`（「り」の未然形。打消の助動詞「ず」に接続するのは未然形） |
| anchor | フィールド自体がこのスキーマに存在しない |
| marker生成後の文字列 | `らず`（`highlight()` は `target` をそのまま `<mark>` に入れるだけなので、データの `target` が誤っていればマーカーもそのまま誤る） |
| marker開始/終了位置 | `example.indexOf("らず")` の位置から4文字（`らず`の文字数） |
| 「ず」が別助動詞か | **はい**。「ず」は打消の助動詞で、「り」の活用表（ら/り/り/る/れ/れ）のどの活用形にも含まれない、独立した語 |
| データ誤りか、markerロジック誤りか | **データ誤り**。`highlight()` 自体は単純な部分文字列一致で正しく動作している。`target:"らず"` という値そのものが「り」の未然形「ら」＋後続の別助動詞「ず」を一つの文字列にしてしまっている |

### 判定

動詞「思ふ」の活用形を問う問題ではなく、**助動詞「り」**の活用形を問う問題。
期待されるmarker範囲は「ら」のみ。「らず」全体をマーカーにすると、
学習者から見て「り」の活用形が「らず」であるかのように誤解させる。

修正案（実施はまだしていない — 監査フェーズのため）:
`target:"らず"` → `target:"ら"` へのデータ修正のみで解消する。マーカー
ロジック (`highlight()`) 自体の変更は不要。

## 既知テストケース2: 「変る」(`kawaru`)

```js
{id:"kawaru",pos:"verb",label:"動詞",lemma:"変る",kind:"ラ行四段活用",
 forms:[F(["ら"]),F(["り"]),F(["る"]),F(["る"]),F(["れ"]),F(["れ"])],
 poem:90,target:"変ら",
 example:"見せばやな雄島の海人の袖だにも濡れにぞ濡れし色は変らず"}
```

（百人一首 90番、殷富門院大輔）

| 項目 | 値 |
|---|---|
| raw quotation | 変更なし。百人一首の歌としての表記を保持すべき |
| raw target | 変更なし。「変ら」（未然形）を出典表記のまま保持すべき |
| analysis key（=lemma兼marker一致キー） | `lemma:"変る"` は見出し語表示にのみ使われ、`target`/`example` の部分文字列一致には使われていない（`.lemma` の用途を全箇所grepして確認済み）。そのため **lemmaだけを変更してもmarker一致ロジックは壊れない** |
| display lemma / display target を分離できる構造か | **現状は分離できていない**。公開版129項目スキーマには `lemma` 1本しかなく、内部QA 910例側にある `displayLemma` / `displayTarget` のような二層構造が存在しない。ただし `lemmaAid` というDOM要素と `kanjiAid` / `targetReading` フィールドは既に一部項目で使われており（例: `document.getElementById("lemmaAid").textContent = 漢字補助：${aid}(${aidReading})`）、**漢字が主表示でひらがなが補助**という向きの構造は既にある。「変る」で欲しいのは逆向き（ひらがな主表示＋任意で漢字補助、または単純にlemma自体をひらがな化）なので、既存の `lemmaAid` 機構をそのまま流用はできない |
| 同種例が他に何件出るか | 129項目のうち **94件** が「lemmaが漢字を含み、かつ `kanjiAid`/`targetReading` フィールドを一切持たない」。ただしこれは母数として粗すぎる（動詞の見出し語は通常漢字表記が普通であり、それ自体は問題ではない）。「変る」が特に問題視される理由は、**現代仮名遣いの送り仮名（わ）と歴史的仮名遣いの送り仮名（は）が送り仮名の有無で区別できず、漢字表記だけでは学習者が正しい歴史的仮名遣いを想起できない**という、ハ行転呼音に関わる特定のパターン。このパターンを機械的に洗い出すには「歴史的仮名遣いで語中語尾がは/ひ/ふ/へ/ほになる動詞」のキュレーションリストが必要で、今回のヒューリスティックでは自動抽出していない（過検出を避けるため）。人間側で対象語彙を選定することを推奨 |

### 判定

- raw quotation（百人一首の歌本文）・raw target（`変ら`）は変更しない。
- `.lemma` は marker一致には使われていないため、`lemma:"変る"` を
  `lemma:"かはる"` に変更する、または新たに `displayLemma:"かはる"` /
  `kanjiAid:"変る"`（現行`lemmaAid`とは逆向きの意味づけになる点に注意）
  を追加するかは人間判断が必要。
- 「漢字を必ず付ける」方針にはしない、という指示のとおり、ひらがなのみの
  表示（`かはる`）を許容する構造にすることを推奨。ただし実装（コード変更）
  は本監査の範囲外。

## 3件目以降（追加発見・人間確認により拡大）: 助動詞28件中17件が同型の逸脱

人間による確認で、`ru_aux`/`raru_aux`の期待値は当初案の「しのばれ」
「あてられ」（先頭の動詞語幹を含む）ではなく、**「れ」「られ」のように
助動詞自身の活用形だけ**であるべきと訂正された。この訂正を受けて
「対象語自身の活用表の値（`forms`、二段構成語は`forms2`も含む）と
`target`が完全一致するか」という、より厳密な基準で助動詞28件全件を
再点検した（詳細は `index-html-129-audit-summary.txt` /
`index-html-129-audit.csv` の `auxExactFormMatch` 列）。

**既にこの基準を満たしている11件**（＝この形式が本来の設計であることの
裏付け）:

「推定される正しいtarget」列のうち `ri_aux`/`ru_aux`/`raru_aux` の3件は
人間により明示的に確認済み。残り14件は「自身の活用形のうち`target`の
末尾に一致する最長の値」を機械的に提案しただけで、**個別の人間確認は
まだ行っていない**。特に `mashi_aux`（`ざらまし`＝「ず」未然形＋「まし」）
のように、先頭が動詞語幹ではなく**別の助動詞**であるケースは、
文法的に一続きの決まった言い回しとして前後を見せる意図的な表示だった
可能性もあり、機械的に「バグ」と断定しない。

この17件は「データ誤り」というよりは、**表示レイヤーの設計方針の不統一**
という性格が強い。`highlight()`関数自体は正しく動作しており（単純部分
文字列一致なので`target`の値さえ確定すれば正しくマークされる）、
問題は一貫していない`target`値の作り方にある。

910例側（内部QA）の助動詞290件については、`normalizedKey`と
`originalTarget`の差異を全件確認したが、清濁表記ゆれ（`ズ`↔`ず`、
`さり`↔`ざり`等、`HANDOFF.md`記載の既知の正規化差）のみで、この種の
「別語混入」は確認されなかった。動詞・形容詞・形容動詞カテゴリについても
同様の混入は今回の長さヒューリスティックでは検出されなかった（過検出
だった3件は`marker-kana-audit-v1.md`に記載のとおり）。
