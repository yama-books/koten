# 歴史的仮名遣い確認ツール 実装計画

作成日: 2026-08-30  
状態: **人の承認待ちの計画案**  
対象仕様: `docs/superpowers/specs/2026-08-30-歴史的仮名遣い確認ツール-design.md`

---

## 1. 目的と境界

本計画は、歴史的仮名遣い確認ツールの一次データ、コンバータ、600件検証、語彙データ工程を、正本を書き換えない一方向パイプラインとして実装する段取りを定める。

今回の発注で実際に作るのは次の3点だけである。

1. 本実装計画
2. `仮名遣い規則_一次データ.md` の人承認待ち案
3. 本書 §7 のコンバータ受入テスト設計

コンバータのコード、600件検証の実行、語彙収集、UI実装は今回行わない。とくに語彙収集は、P1c の600件検証と人の裁定が終わるまで開始しない。

全成果物は生成AIによる案であり、一次資料の内容・公開問題・正解・正本を確定しない。AI案には `proposedBy: "ai"`、未承認状態には `reviewStatus: "pending"` を持たせる。

## 2. 実装上の確定事項

| 項目 | 計画への反映 |
|---|---|
| 公開単位 | 製品固有コードは `packages/kanazukai`、公開先は `/kanazukai/`。 |
| 共有層 | 製品非依存の読込、保存、習熟度、共通UIは `packages/shared`。生成JSONの共通読込は `packages/shared/src/data/load.ts`。 |
| 習熟度単位 | `itemKey = wordId`。`ruleId` は加点対象にせず、分析・推薦の次元にする。 |
| 正本と生成物 | Markdownを正本、JSONを再生成可能な派生物とする。生成工程から正本へ書き戻さない。 |
| 公開制限 | `reviewStatus !== "human-confirmed"` の規則・語・問題を公開出題へ含めない。 |
| 規則数 | 16規則。単語出題13、句モードのみ2、記録のみ1。 |
| 実装順 | P0 → P1a → P1b → P1c を直列とし、語彙収集 P2 以降は P1c 後に開始する。 |
| H-12 | `CONSTITUTION.md` の改訂は人が決める。本計画では変更しない。 |
| H-13 | 書き出し形式の `product` と `schemaVersion` は、`docs/IMPLEMENTATION_PLAN.md` の P4（保存・移行）着手前に人が決める。 |

## 3. 資源配分と典拠確認の強度

単純な候補抽出に上位モデルを使わず、判断の必要な不一致へ資源を集中する。

| 作業 | 担当の目安 | 確認方法 |
|---|---|---|
| 既存資料から候補語・出典位置を抜き出す | Luna low | 機械的な抽出、重複排除、規則タグ候補まで。確定フラグは付けない。 |
| 規則カバレッジと空きセルを集計する | Luna low またはスクリプト | 件数・重複・規則×難度の機械検査。 |
| 規則どおりの単純な読みを照合する | 決定的コンバータ＋一括確認候補 | 人が仕組みと代表標本を確認した場合に限り、一括承認の候補にできる。確認者・確認日・根拠記録は省略しない。 |
| 600件の差分抽出・一次分類候補 | 下位モデルまたはスクリプト | 全件一覧と分類候補を作るだけ。最終裁定はしない。 |
| 規則の穴、例外、固有名詞、一次資料の異同 | 人（必要に応じ上位モデルが整理補助） | 1件ずつ根拠を見て裁定する。 |
| `human-confirmed` への変更 | 人 | AIは変更しない。 |

「二資料照合」は、同じ読みを毎回ゼロから調査するという意味にはしない。承認済みの正本、規則に基づく決定的変換、確認機構の代表標本を再利用し、機械的一致はまとめて人が確認できる形にする。一方、差分・同綴異義・例外・固有名詞は一括承認から外す。

### 4.1 仮名遣いデータ工程の提案

現在の `tools/build-data/` は百人一首専用である。既存工程を製品共通の巨大な条件分岐へ変えず、次の製品別入口を追加する案を採る。

```text
入力（読み取り専用）
  仮名遣い規則_一次データ.md
  仮名遣い語彙_一次データ.md       P2以降
  review/kanazukai/*                人が書き込む確認台帳

  ↓ tools/build-data/kanazukai（提案）
  parse → normalize → apply-review → validate → emit

出力（再生成可能・手編集禁止）
  packages/kanazukai/src/data/generated/rules.json
  packages/kanazukai/src/data/generated/words.json
  packages/kanazukai/src/data/generated/manifest.json
```

この構成は、ルート正本・`tools/build-data/`・`tests/data/`・製品別 `generated/` という既存の分類内に収まる。提案を採用する前に人が配置を確認する。別の新規領域が必要になった場合は S-C で停止する。

## 5. フェーズと依存関係

```text
P0 規則案
  → P1a 受入テスト設計
  → P1b コンバータ実装
  → P1c 600件検証・人裁定
  → P2 候補プール
  → P3 v0=60語
  → P4 二資料照合
  → P5 CI
  → P6 v1=180語
  → P7 例外20語
```

P1c が唯一の直列ボトルネックである。P2以降では供給源ごとの候補抽出だけを並行化できる。

## 6. 各フェーズの仕様

```text

実施内容:
  1. 16規則を ruleId を変えずに起こす。
  2. label、説明、例、出題区分、典拠、親規則IDを記録する。
  3. 全行に proposedBy: "ai" と reviewStatus: "pending" を付ける。
  4. S1、D1-a、K1、L1〜L3の弱い典拠・翻案を明記する。
作成・変更予定ファイル:
  作成: 仮名遣い規則_一次データ.md
```

```text
フェーズ名: P1c 百人一首600件検証
目的: 100首×5句＋作者名の600件で規則表とコンバータを検証し、語彙収集前に穴と例外を洗い出す。
前提: P1b完了。2つの読み正本が100首・各6欄で対応すること。現代読み表の空行を正しく越えて読むこと。
実施内容:
  1. 番号と欄名で歴史的読み・現代読みを結合する。
  2. 600件すべてを変換し、期待値、実出力、適用規則、差分を一覧化する。
  3. 機械的な分類候補付けは下位モデルへ委譲できるが、最終裁定は人が全不一致を見る。
  4. 分類別件数と総数600の一致を検査する。
作成・変更予定ファイル:
  作成候補: tools/build-data/kanazukai/verify-hyakunin.ts、
            tests/data/kanazukai/hyakunin-600.acceptance.test.ts、
            review/kanazukai/hyakunin-conversion.yaml
  生成候補: review/kanazukai/generated/hyakunin-conversion-report.json
変更しないファイル: 百人一首の一次資料4点、規則正本、現代読み表の空行。
依存関係: P1b。
人間確認: 全不一致を、規則の穴・語彙例外・固有名詞・一次資料異同・実装不備等へ裁定する。
対象テスト: §7.4の600件事前検査、一覧の列、排他的分類、分類件数合計、再現性。
受入条件: 600件が欠落・重複なく一覧化され、全不一致に人の裁定またはpendingが明示される。
ロールバック: 生成報告は再生成する。人の裁定台帳は削除せず、誤記を追記訂正する。
停止条件: S-B。規則追加なしに説明できない不一致は、人の裁定まで先へ進めない。
概算規模: 中〜大（差分抽出1日、裁定件数に応じ2〜7日以上）。
```

### P4 二資料照合と確認状態確定

```text
フェーズ名: P4 二資料照合と確認状態確定
目的: v0語の読み・語義・規則タグを確認し、公開可能な状態を人が確定する。
前提: P3完了。H-13が `docs/IMPLEMENTATION_PLAN.md` のP4（保存・移行）着手前に人によって裁定されている。
実施内容:
  1. 各語を二資料で照合し、根拠と差異を確認台帳に記録する。
  2. 決定的変換で一致する単純語は、人が機構と代表標本を確認した場合に一括確認候補にする。
  3. 不一致、例外、K1、固有名詞、許容表記は個別確認へ回す。
  4. 人だけが human-confirmed を付ける。
作成・変更予定ファイル:
  変更: 仮名遣い語彙_一次データ.md、review/kanazukai/*
  作成候補: review/kanazukai/batch-evidence.yaml
変更しないファイル: 原資料、規則正本、CONSTITUTION.md、converterの期待値。
```

## 7. コンバータ受入テスト設計（成果物C）

### 7.1 規則別の適用・非適用

「適用」は文字が変わる規則だけでなく、例外として保持する規則と、記録のみの恒等規則を含む。各fixtureは `input`、`context`、`expected`、`expectedRules`、`mustNotApply` を持つ。

| ruleId | 適用または保持の期待例 | 非適用の期待例 |
|---|---|---|
| `H1` | `にほひ → におい`、`笑ふ → わらう` | `はな → はな`、`はつはな → はつはな`、句の `花は → 花は` |
| `H1-a` | 語頭指定つき `はな → はな` | `にほひ → におい` には `H1-a` を付けない |
| `H1-b` | 複合境界つき `はつはな → はつはな`、`をりふし → おりふし` | 単純語 `にほひ` の語中ハ行を保護しない |
| `H1-c` | 助詞指定つき `花は → 花は`、`都へ → 都へ` | 名詞 `いへ → いえ` の末尾を助詞として保護しない |
| `W1` | `ゐる → いる`、`こゑ → こえ` | すでに現代表記の `いる → いる`、`こえ → こえ` |
| `W2` | `をとこ → おとこ`、`とを → とお` | 助詞指定つき `本を → 本を` |
| `W2-a` | 助詞指定つき `本を → 本を` | 名詞 `をとこ → おとこ` を保護しない |
| `D1` | `もみぢ → もみじ`、`みづ → みず` | `D1-a` 指定の `つづく → つづく` |
| `D1-a` | 例外指定つき `つづく`、`ちぢむ`、`みかづき`、`はなぢ` を保持 | 通常語 `もみぢ → もみじ` を保護しない |
| `K1` | 語義指定つき `くわし（菓子） → かし`、`ぐわん（願） → がん` | `くはし（詳し） → くわし` へ `K1` を適用しない |
| `N1` | 文法形指定つき `らむ → らん`、`ねむ → ねん` | 動詞 `産む（うむ） → うむ` の「む」を変えない |
| `L1` | `かうし → こうし`、`あふぎ → おうぎ` | `いうげん`、`せうと` に `L1` を適用しない |
| `L2` | `いうげん → ゆうげん`、`きう → きゅう` | `かうし`、`せうと` に `L2` を適用しない |
| `L3` | `せうと → しょうと`、`けふ → きょう` | `かうし`、`いうげん` に `L3` を適用しない |
| `L4` | `ようい → ようい` を記録できる | 文字変更、チップ表示、出題、変更済み規則列への追加をしない |
| `S1` | `しやう → しょう`、`きつと → きっと` | 小書き済みの `しょう → しょう`、`きっと → きっと` |

`H1` は通常規則、語頭、複合語後部、助詞、P1cで見つかる語彙的例外を別fixtureにする。文脈なしに複合語・助詞・語義・文法形を推測した結果を受入条件にしない。

### 7.2 競合と適用順

実装は、まず明示された例外・保護範囲を確定し、通常規則を適用する。観測可能な順序として、`H1` は `L1`〜`L3` より前、`S1` は長音変換後とする。互いに可換な規則の内部順は固定せず、最終出力と `appliedRules` を検査する。

| 入力 | 期待出力 | 必須規則・順序 |
|---|---|---|
| `ひとごゑ` | `ひとごえ` | `W1` |
| `かはづ` | `かわず` | `H1` + `D1` |
| `をりふし` | `おりふし` | `W2` を適用し、複合語後部の `ふ` は `H1-b` で保護 |
| `たふとし` | `とうとし` | `H1` で `たうとし`、続いて `L1` |
| `いへぢ` | `いえじ` | `H1` + `D1`（`W1`ではない） |
| `てうづ` | `ちょうず` | `L3` + `D1`、最終表記は `S1` の小書きを満たす |
| `けふ` | `きょう` | `H1` で `けう`、続いて `L3`、最後に小書き |
| `あふぎ` | `おうぎ` | `H1` で `あうぎ`、続いて `L1` |
| `つづく` | `つづく` | `D1-a` の保護が `D1` より優先 |
| `はつはな` | `はつはな` | `H1-b` の保護が `H1` より優先 |
| 句 `花は` | `花は` | `H1-c` の保護が `H1` より優先 |
| 句 `本を` | `本を` | `W2-a` の保護が `W2` より優先 |

部分適用の中間値は誤答診断に使う。例として `てうづ` では、無適用、`D1`のみ、`L3`のみ、全適用の4状態を生成し、正解判定の根拠には決定的規則だけを用いる。

### 7.3 入力正規化

採点用の正規化と、歴史的表記を現代表記へ変えるコンバータは別関数にする。次を固定する。

| 入力・操作 | 期待 |
|---|---|
| 分解された濁点（例: `か`＋結合濁点） | Unicode NFC後の同じ仮名と一致する |
| `チョウズ` | カタカナをひらがなへ直し、`ちょうず` と一致する |
| 前後の半角・全角空白 | 除去する |
| 語中の空白 | 勝手に除去しない |
| `ちょーず` | 長音符を `う` へ直さず、不正解にする |
| IME変換中 | `compositionend` 前は採点しない |
| Enter | 送信へ割り当てず、独立ボタンだけで採点する |

正規化後も、正解集合との完全一致で採点する。許容正解がある語は、主正解と承認済み許容正解の集合を使うが、v1では許容併記語を出題対象から外す。

### 7.4 百人一首600件検証

#### 対象と事前検査

- 番号1〜100の各首について、5句と作者名の6欄を対象にする。
- 歴史的仮名遣い600件を変換し、同じ番号・欄の現代仮名遣い600件と比較する。
- 2つの表を行位置でなく `番号 + 欄名` で結合する。
- 現代仮名遣い表の途中の空行で読み取りを止めない。50件で終わった場合はテスト失敗とする。
- 事前に、各表100首、番号1〜100の欠番・重複なし、各首6欄、合計600件を検査する。

#### 一覧の列

```text
歌番号 / 欄 / 歴史的入力 / 期待現代表記 / コンバータ出力 /
一致可否 / 適用規則 / 中間値 / 分類候補 / 人の最終分類 /
reviewStatus / 裁定メモ
```

#### 不一致分類

最終分類は人が選ぶ。AIまたはスクリプトは `分類候補` までしか付けない。

| 分類 | 意味 | 次の処理 |
|---|---|---|
| 一致 | 期待値と出力が一致 | 集計のみ |
| 実装・パーサ・正規化の不備 | 既存規則で説明できるのに処理が誤る | コードを修正し再実行 |
| 既知の語彙的例外 | 規則表を変えず語単位で扱う | 例外区分へ記録 |
| 固有名詞・作者名 | 固有名詞等で一般規則を一律適用できない | 個別根拠を確認 |
| 一次資料の異同・誤り候補 | 2つの正本または採用読みの確認が必要 | 一次資料判断として人へ上げる |
| 規則不足・規則表の穴 | 既存16規則では説明できない | S-Bで停止し、人へ裁定を求める |
| 裁定待ち | 上記を一意に決められない | 公開・語彙収集へ進めない |

分類件数の合計が600であること、未分類が0またはすべて明示的な `裁定待ち` であることを検査する。不一致を自動的にバグ扱いしない。

#### 予想される不一致

- `はは`（母）のような `H1` の語彙的例外と、`ほほ`（頬）のような通常変換の対比
- 作者名・固有名詞に由来する一般規則の適用外
- 複合語境界、助詞、D1-a、N1など、文字列だけでは判定できない文脈
- `K1` のように漢字・語義が必要な同綴異義
- 「ぢ・づ」の許容表記または二語連合
- 発音を長音符で示す資料と、現代仮名遣いの表記を混同した差分
- 途中の空行による誤パース、欄の誤結合、正規化の不備
- 既存16規則では説明できず、S-Bの裁定が必要になる差分

## 8. 人間確認と停止条件

| 条件 | 本計画での扱い |
|---|---|
| S-A: 16規則の誤り・重複・取りこぼし | 規則を直さず停止し、箇所・例・根拠を報告する。 |
| S-B: 600件で規則追加なしに説明できない不一致 | P1cで停止し、語彙収集を始めない。 |
| S-C: §4.2の分類外ファイルが必要 | 新規配置を作らず、人へ裁定を求める。 |
| S-D: 原資料だけが典拠で本計画の表記では根拠を示せない | 詳細を公開側へ写さず、人へ確認を求める。 |
| S-E: 設計書と憲章の不整合 | 下位文書を直さず停止する。 |

現時点では、確定設計の例や規則に「誤り」と断定できるものは見つけていない。複合語・助詞・語義・文法形を文字列だけから決められない点は、規則の誤りではなくコンバータが明示的文脈を必要とする実装条件として扱った。これが設計意図と異なる場合は、P1b着手前に人が裁定する。

## 9. 本計画で独自に決めた提案

以下は確定仕様の転記ではなく、取り返し可能な実装提案である。

1. 仮名遣い用生成工程を `tools/build-data/kanazukai/`、データテストを `tests/data/kanazukai/` に分ける。
2. コンバータは、文字列だけでは決まらない助詞・複合語・語義・文法形を明示的な文脈として受け取る。
3. 適用順は、例外保護 → 通常規則、`H1` → `L1`〜`L3` → `S1` とし、可換な規則の内部順はAPI契約にしない。
4. 600件不一致の分類軸を §7.4 の7区分とする。
5. 単純な機械的一致は、人が機構と代表標本を確認した場合に限って根拠付き一括確認の候補とし、例外・差分は個別確認へ回す。

いずれも人の承認前は提案であり、正本・公開問題・正解を確定しない。
