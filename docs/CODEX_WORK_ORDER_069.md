# 発注069準備書：作者問題の歌を縦書きへ戻し、選択肢を縦書きの札にする

- 作成：2026-09-06、Sol役＝Opus 5。**依頼者の実機確認（公開版 `ce1c596`・64番）から出た。**
- 状態：**裁定済み。ただし着手は発注068の完了後**（同じファイルを触るため。§0.1）。
- 由来：作者問題の画面で、**縦書き設定なのに歌が横書き右揃えで出る**。**選択肢が5つとも墨色べた塗りで、うるさい。**

## 0. 何が起きているか（**原因は特定済み。調査し直さなくてよい**）

### 0.1 歌が横書きになる理由

`styles.css` に**縦書きを打ち消す1行がある。**

```css
.question-text--author .question-poem--author { ...; text-align: start; writing-mode: horizontal-tb; }
```

親（`.question-text--vertical .question-poem`）が `direction: rtl` を持つため、
**打ち消された結果が「横書き・右揃え」として出る。** 実機で見えているのはこれである。

`Session.tsx` 630行目も、作者問題のときだけ**歌をひとかたまりの文字列**として出している。

```tsx
<div class="question-poem question-poem--author" lang="ja">{question.prompt}</div>
```

穴埋めの側は句ごとに `.question-line`（`writing-mode: vertical-rl`）へ割っている。
**作者問題だけがその器に載っていない。**

### 0.2 選択肢がうるさい理由

`Session.tsx` 668行目で、**候補5つすべてに `class="primary"` を付けている。**
`.primary` は `background: var(--color-ink); color: var(--color-paper); font-weight: 700` ——
**主要操作を1つだけ示すための印である。** それが5つ横並びになっている。

### 0.3 これはデザインシステム違反である（**好みの問題ではない**）

`docs/DESIGN_SYSTEM.md` の設計原則より。

- **原則2**：「歌・設問・**選択肢の対象**は縦書き、ボタン・設定・進捗・説明・エラーは横書き。
  **レイアウト都合で本文を横書きにしない。**」→ **歌も選択肢も違反している。**
- **原則1**：「内容を主役にする。**装飾は意味を持つ小さな印に限る。**」→ 墨色べた塗り5つが主役を奪っている。

**発注062 の落ち度である。** 選択肢を選ばせるUIがこのアプリに存在せず、新設したときに
縦書きの器へ載せずに済ませた。**起草者（Sol役）が発注062で「縦書きに載せること」を書かなかったのが原因である。**

## 1. 工程1：作者問題の歌を縦書きに戻す

### 1.1 裁定

- **作者問題でも、歌は設定（縦書き／横書き）に従う。** 作者問題だけの例外を作らない。
- **穴埋めと同じ器に載せる。** 句ごとに `.question-line` へ割り、`.question-text--vertical` の中に置く。
  **新しい縦書きの仕組みを作らない。**
- **句の分割はデータにある。** `poems.json` の各首は `ku: [5句]` を持ち、
  **`Session` は `poems` を props で受け取っている**（`packages/hyakunin/src/ui/screens/Session.tsx` の `poems = []`）。
  `question.poemId` から引いて `ku` を使う。**生成JSONを作り直さない。**
- **`poems` が空のとき（試験など）は、いまと同じく `question.prompt` を1つの列として出す。**
  **落ちないこと。** ここは退避であって、**本番で使われる経路ではない。**
- `.question-text--author .question-poem--author` の **`writing-mode: horizontal-tb` を消す。**

### 1.2 受入条件（工程1）

- 縦書き設定のとき、作者問題の歌が**縦書きで出ること**。**`writing-mode` を DOM から読んで確かめる。**
- **横書き設定のときは横書きで出ること。両方向で確かめる**——片方だけでは切り替えが死んでいても緑になる。
- **句ごとの列が5つ**あること（64番なら「朝ぼらけ／宇治の川霧／たえだえに／あらはれわたる／瀬々の網代木」）。
- `poems` が空でも**例外を投げず**、歌が読めること。
- 穴埋めの画面の見え方が**変わらないこと**（既存の釘が全部緑のまま残ること）。

## 2. 工程2：選択肢を縦書きの札にする

### 2.1 裁定（**依頼者の提案どおり。可能である**）

- **選択肢を縦書きにし、右から左へ並べる。** 位置は歌の下、いまの「作者を選んでください。」の場所でよい。
- **`class="primary"` をやめる。** 候補は互いに対等であり、**主要操作は1つも無い。**
  既定のボタン（`--rule-thin` の枠＋`--color-surface`）にする。
  **選ばれたあとの強調は既存の作法に合わせる**（`aria-pressed` の見せ方＝`--color-focus` の枠と `--color-surface-soft`）。
- **長い名前は2列以上に折り返してよい**（依頼者裁定）。
- **折り返すと横幅が足りなくなる。** 320px・文字200%で、1列は約48px、5列で約272px と収まるが、
  **2列へ折り返すと約520pxとなり収まらない。**
  → **`.question-text--vertical` と同じく、横スクロールできる領域として扱う。**
  **走査からは「名前で」除外する**（059 F-2 の縦書き器と同じ扱い。**ディレクトリや親要素でまとめて外さない**）。
- **「わからない」は横書きのまま、選択肢の外に置く。** これは選択肢ではなく操作である（原則2）。

### 2.2 受入条件（工程2）

- 候補のボタンが `writing-mode: vertical-rl` で描かれ、**右から左へ並ぶこと。**
- **`class="primary"` を持つ候補が0件**であること。**候補が1件以上ある状態で数えること**——
  候補0件の画面で数えても、実装が無くても緑になる。
- **押すと従来どおり採点されること。** `submit(candidate, "choice")` の経路を変えない。
  **既存の作者問題の試験を1本も落とさないこと。**
- 「わからない」が横書きのまま残ること。
- 320px・文字200%で違反0。**作者問題の走査群は既にある**（8件）。
  **横スクロールを許す要素は名前で除外し、除外した根拠を発注書に書くこと。**
  **「通らないから外す」は認めない。**

## 2.5 工程3：フィードバック画像の白い背景を消す

### 2.5.1 調べた事実（**調査し直さなくてよい**）

- 画像は3枚：`assets/feedback/` の `correct-maru`・`needs-review-check`・`perfect-hanamaru`。
- **配信されている `.webp` は3枚とも透明度を持たない**（VP8 lossy、ALPH チャンクなし）。
- **原本の `.png` も3枚とも RGB（colortype 2）で、透明度を持たない。**
  **白は画像の中に焼き込まれている。** 原本から作り直しても、そのままでは透過にならない。
- 白を抜く加工は、**手描きの線の縁に白い縁取りを残す**（アンチエイリアスのため）。**採らない。**

### 2.5.2 裁定

- **画像を作り直さない。CSS で解決する。** フィードバック画像に **`mix-blend-mode: multiply`** を当てる。
  白は乗算で背景色そのものになるため、**`--color-paper` が何色でも背景と一致する。**
  **色の値を画像に合わせて固定しない**——固定すると、背景色を変えたときに白い箱が戻る。
- **3枚すべてに当てる**（依頼者の「他の画像も同様」）。個別に指定せず、**画像を出す部品の1か所**で当てる。
- **線の色は変えない。** 乗算で紙色と混ざり、わずかに温かくなるのは想定どおりである。

### 2.5.3 受入条件（工程3）

- 3枚とも、**画像を出す要素に `mix-blend-mode: multiply` が効いていること**（計算後の値を読んで確かめる）。
- **画像そのもの（`assets/feedback/**` と `.webp`）を1バイトも変えないこと。**
  `git diff --numstat -- assets` が **0行**であること。
- 既存の画像に関する釘（`img[src*="correct-maru"]` を見る試験など）が**緑のまま残ること。**

## 2.6 工程4：作者の正解表示と「わからない！」

### 2.6.1 裁定（**依頼者指示・2026-09-06**）

**作者問題の正解表示を、次の形にする。**

```
正解：権中納言定頼　ごんちゅうなごんさだより
（歴史的仮名遣い：ごんちゆうなごんさだより）
```

- **上段は「作者　読み（現代仮名遣い）」。** 区切りは全角空白1つ。
- **下段は歴史的仮名遣いとの異同があるときだけ出す。** 同じなら**行そのものを出さない。**
  **対照するものが無い行は、読み手に差があると誤解させる**（これは既存の作法と同じ理屈である）。
- **`正解：` の接頭辞は残す**（起草者判断）。本番の採点一覧では複数行が並ぶため、
  どれが正解の行かを言葉で示す必要がある。**依頼者が不要と判断したら外してよい。**
- **これは作者問題だけの形である。** 歌本文の表示（`正解：白妙の（しろたへの）` ＋ `△しろたえの（現代仮名遣い）`）は
  **1文字も変えない。** 歌本文は歴史的仮名遣いで答えさせるため、歴史的が主で現代が対照である。
  **作者は選択式で綴りを問うていないため、主従が逆になる。**
- 判定は問題の種別（`type === 'author'` / `skill === 'author'`）で行う。
  **呼び出し側から明示的に渡すこと。** 表示部品が読みの中身から推測しない。

**「わからない」ボタンの表記を「わからない！」にする。**

- **見つけ方が厳密一致の試験が4本ある**（`tests/screen/session.test.tsx`）。**すべて更新すること。**
  **文言だけ変えて試験を直さないと、4本が同時に赤くなる。**

### 2.6.2 受入条件（工程4）

- 異同がある作者（64番・権中納言定頼）で、**2行とも出ること。**
- **異同が無い作者で、下段が出ないこと。** **両方向で確かめる**——
  片方だけでは「常に出す」実装でも緑になる。**異同の無い作者を正本から1つ選んで fixture にすること。**
- 上段が「作者　読み」の順であること。**読みは現代仮名遣いであること**（歴史的を上段に出さない）。
- **歌本文の表示が変わらないこと。** 既存の釘（`正解：白妙の（しろたへの）`、`△しろたえの（現代仮名遣い）`）が
  **全部緑のまま残ること。**
- 「わからない！」で見つかること。**「わからない」（！なし）で見つかる箇所が0件**であること。
- 本番の採点一覧・紙の自己採点でも、作者問題の行が同じ形で出ること。
