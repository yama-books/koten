## 1. 工程1：広い画面で縦書きが右へ流れる

### 1.1 何が起きているか（実機・PC幅）

- 出題画面：**歌は中央寄り、答え欄とボタンは左端いっぱい**で、軸が揃わない（④）。
- 作者問題：**選択肢が右端、「わからない！」が左端**と、押すものが左右に割れる（⑥）。
- 閲覧画面：**作者名と「作者名を見る」が右端に張り付き**、歌との間が大きく空く（⑭）。

**原因は同じである。** 縦書きの器は「右から左へ、幅いっぱいに広がる」作りで、
**狭い画面では詰まって中央に見えていただけ**である。
**`check:overflow` は 320/375/414/768px までしか測っておらず、それより広い幅を誰も一度も見ていない。**

### 1.2 裁定

- **縦書きの器に読みやすい最大幅を与え、中央に置く。** 幅いっぱいに広げない。
- **作者名が歌の「右側」にあること自体は正しい**（縦書きは右から読む。百人一首の札も作者は右）。
  **変えるのは、右端へ張り付いて歌から大きく離れることだけである。**
- **押すもの（選択肢・「わからない！」・「次の歌」）が左右に散らないようにする。**
- **狭い画面の見え方を変えないこと。** いまスマホでは中央に収まっている。**そこを壊さない。**
- 最大幅の書き方は**既存に揃える**（`.onboarding__dialog`・`.interrupt-dialog` の
  `width: min(100%, 30rem)` が先例）。**新しい流儀を作らない。**

### 1.3 受入条件（工程1）

- **`check:overflow` に広い幅を足す。** 現在の `widths` は 320/375/414/768。
  **1024 と 1440 を足し、全走査群で違反0にすること。**
  **件数の門も新しい幅に合わせて更新すること。**
- **1024px と 1440px で、出題画面・作者問題・閲覧画面の3つを測ること。**
- **「歌の器の中心が画面の中心からどれだけ離れているか」を数値で見る試験を1本置くこと。**
  **見た目で判断しない。**
- **320px の既存の走査が全部緑のまま残ること。** 狭い側を壊していないこと。

## 7.5 工程8：復元カードの再整理（**「◯回目」は順番を表していない**）

### 7.5.1 何が起きているか（実機）

```
範囲 1番〜100番・20首ずつに分けて全5回
いまは3回目（このまとまりはあと20首）・範囲全体であと88首
進み 12首/100首  ▓░░░░
続きから始めると、この3回目のなかから8問を出題します。
```

**「3回目なのに、そのまとまりは1首も手をつけていない（あと20首＝満量）」**という表示になっている。

**破綻ではない。** `nextChunkIndex` は「**未確認の首がいちばん多いまとまり**」を選ぶ（同数なら先頭）。
確認済み12首がまとまり1・2に散っていれば、まとまり3・4・5はどれも20首のまま。
**同数なので先頭のまとまり3が選ばれる。数字は実装と整合している。**

**壊れているのは言葉である。** 「いまは3回目」と書けば、誰でも「5回のうち3回目まで進んだ」と読む。
実際の意味は「3番目のまとまりが、いちばん手つかずなので次に出す」である。
**言葉が、数字の意味していないことを主張している。**

### 7.5.2 裁定

- **「◯回目」「◯セット目」という順番の言い方をやめる。**
  順番を表す語である限り、進捗と誤読される。
- **代わりに、次に出すまとまりの番号範囲を書く。** 嘘にならず、
  学習者には「次にどの歌をやるのか」が分かって順番より役に立つ。
- **「続きから始めると、この◯回目のなかから◯問を出題します。」を削除する。**
  **削除しても意味が通る**（依頼者確認済み）。
- バーの横は「**12首/100首**」だけ（工程2の「進み」削除と揃う）。
- 範囲の行を**枠で囲むなどして、まとまりの説明と現在地を視覚的に分ける。**

**想定する形**（文言は実装者が整えてよい。**順番を名乗らないことだけは外さない**）：

```
範囲 1番〜100番（20首ずつ・全5まとまり）
次は 41番〜60番（20首）
12首/100首  ▓░░░░
```

### 7.5.3 受入条件（工程8）

- **復元カードに「◯回目」「◯セット目」が0件**であること。
  **走査対象が空でないことを先に示すこと**（復元カードが出ている状態で数える）。
- **次に出すまとまりの番号範囲が出ていること。**
  **`nextChunkIndex` が選んだまとまりと一致すること**——別の数を表示しないこと。
- 「続きから始めると…」の行が**出ないこと**。
- **まとまりが1つ（20首以下）のときの表示を壊さないこと**（発注066 の釘が全部緑のまま残ること）。
- 320px・文字200%で違反0。**復元カードの走査群は既にある**（16件）。

## 7.6 工程9：「回」がまとまりとセッションの2つを指している

### 7.6.1 何が起きているか

ホームに次の2行が並んでいる。

```
穴埋めと作者の問題を交互に出します。1回の学習は8問です。
1番〜100番は20首ずつ全5回に分かれます。まず1回目から始めます。
```

**同じ「回」が2つの違うものを指している。**

- 「全5回」の回 ＝ **まとまり**（20首の束）
- 「1回の学習」の回 ＝ **1セッション**（8問／10問）

**20首のまとまりは8問では終わらない。** ところが「全5回」と書くので、
**「5回やれば100首終わる」と読める。実際は全く終わらない。** これが混乱の正体である。

**さらに2つ、事実と違う記述がある。**

1. **「交互に出します」は嘘である。** `quick` の割合は**穴埋め3：作者1**で、交互ではない
   （8問なら穴埋め6・作者2）。
2. **「1回の学習は8問です」は `quick` だけの数である。** 他の入口は10問
   （`ENTRY_RULES`：`quick` 8、`view`・`learn`・`author`・`exam` は 10）。
   **どの入口の話なのかを書いていないため、「10問から8問に減った」と読める。**

### 7.6.2 裁定

- **「回」はセッション（1回の学習）だけに使う。** まとまりには使わない。
  **「全5回」をやめ、「5つのまとまり」のように個数で言う。**
- **「穴埋めと作者の問題を交互に出します。」→「穴埋めと作者の問題の両方を出します。」**（依頼者指示）。
  **これは文言の好みではなく事実の訂正である。**
- **「〇番〜〇番は」→「〇〜〇番だと」**（依頼者指示）。
- **問数が入口によって違うことが分かるようにする。**
  いまの文はホームの「とりあえず始める」の直上にあるので、
  **「とりあえず始める」の説明であることが読み取れる形にする。**
  **他の入口の問数まで並べない**（増やすと、また読み手が混乱する）。

### 7.6.3 受入条件（工程9）

- ホームの説明に**「全◯回」の形が0件**であること。**走査対象が空でないことを先に示すこと。**
- 「交互に」が**出ないこと**。「両方を」が出ること。
- 「〇〜〇番だと」の形になっていること。
- **`ENTRY_RULES` を1つも変えないこと**（`git diff --numstat -- packages/hyakunin/src/domain/entry.ts` が0行）。
