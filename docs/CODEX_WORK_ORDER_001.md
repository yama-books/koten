## 2. 入力データの形（実測済み・再調査不要）

3 ファイルとも同じ形の Markdown パイプ表である。

```
| # | 作者 | 初句 | 二句 | 三句 | 四句 | 五句 |
|---:|---|---|---|---|---|---|
| 1 | 天智天皇 | 秋の田の | かりほの庵の | とまをあらみ | わが衣手は | 露にぬれつつ |
```

実測結果（`docs/IMPLEMENTATION_PLAN.md` §2.1）:

| 検査 | 3 ファイルとも |
|---|---|
| 番号行 | 100 行 |
| 番号 | 1〜100、欠番なし、重複なし |
| 列数 | 全行 7 列 |
| 空セル | なし |

歴史的仮名遣い・現代仮名遣いの 2 ファイルは、第 2 列が作者名ではなく**作者の読み**である。列見出しが `作者（歴史的仮名遣い）` / `作者読み` と異なるので、見出し文字列でのマッチに依存しないこと。

各ファイルの末尾には表の後に注記セクションがある。**表の行だけを拾い、注記は別途扱う。**

### 2.1 表が空行で分断されている場合がある（重要）

**`百人一首_読み_現代仮名遣い.md` は、表の途中に空行があり 2 ブロックに分かれている。**

```text
行  7-58    ヘッダ行 + 区切り行 + 1〜50 番
行  59      空行            ← ここで止まると 50 件しか取れない
行  60-109  51〜100 番      ← 継続ブロック。ヘッダ行が無い
行  110 以降 注記セクション
```

他の 2 ファイル（`本文・作者`、`歴史的仮名遣い`）は分断がなく 100 行連続である。

したがってパーサは次を満たすこと。

- **「ヘッダの次の空行まで」で読み終えない。** 空行を挟んだ継続ブロックも同じ表として扱う。
- **継続ブロックにヘッダ行が無いことを前提にする。** ヘッダの有無で表を識別しない。
- 拾い方の推奨: ファイル全体から `|` で始まる行を集め、**第 1 列が数字の行だけ**をデータ行とする。ヘッダ行と区切り行（`|---|`）は第 1 列が数字にならないため自然に除外される。注記セクションに表が無いこともこの方法なら影響しない。

**このずれは一次資料の欠損ではない。** 3 ファイルとも 1〜100 が過不足なく揃っていることを実測で確認済みである（§2 の表）。**空行を消す等、一次資料を修正してはならない。** パーサ側で吸収すること。

なお V-01（1〜100 が過不足なく 1 回ずつ）は、この分断でパーサが 50 件しか取れなかった場合に失敗する。V-01 を先に実装すれば、この症状は自動的に検出される。

`百人一首_読み_異同確認.md` は形が異なる。`| 歌番号 | 項目 | PDF／現行転記 | 公開資料の異同 | 判定・採用推奨 | 根拠 |` の 6 列表と、末尾の箇条書きからなる。

## 3. 成果物

### 3.1 パーサ

| ファイル | 責務 |
|---|---|
| `tools/build-data/paths.ts` | 入出力パスの単一定義（D-06 後の移動に備える） |
| `tools/build-data/parse-table.ts` | Markdown パイプ表の汎用パーサ。列数・番号の連続・空セルの異常で**例外を投げる**（読み飛ばさない） |
| `tools/build-data/parse-poems.ts` | 本文・作者一次データ → 中間表現 |
| `tools/build-data/parse-readings.ts` | 歴史的／現代仮名遣い → 中間表現 |
| `tools/build-data/parse-variants.ts` | 異同確認 → `variants.json` |
| `tools/build-data/normalize.ts` | NFC 正規化。全角空白・長音・小書きの扱いを固定。踊り字は正本側で展開済みのため追加展開しない |
| `tools/build-data/hash.ts` | 入力ファイルの sha256 |
| `tools/build-data/emit.ts` | 生成 JSON の書き出し。キー順を固定し、再現性を保証する |
| `tools/build-data/validate.ts` | §4 の検査群 |
| `tools/build-data/index.ts` | `parse → normalize → validate → emit` の一方向実行 |

### 3.2 出力（形。`docs/IMPLEMENTATION_PLAN.md` §5.2 と同じ）

```text
poems.json[]        cardNo, poemId, ku[5], text, kami, shimo,
                    author { canonical, aliases[], confirmed },
                    reading { historical{ku[5],author}, modern{ku[5],author}, status },
                    sourceRef, dataVersion

variants.json[]     cardNo, field, adopted, alternatives[],
                    kind("異本文"|"異表記"|"読み方式"), decision, evidenceUrls[]

manifest.json       dataVersion, generatorVersion, generatedOn(日付のみ),
                    sourceHashes{ファイル名: sha256}, counts{...}
```

規約:

- `poemId` は `"p" + ゼロ埋め 3 桁の cardNo`（例 `p001`）。
- `text` は `ku[5]` の連結。`kami` は初句＋二句＋三句、`shimo` は四句＋五句。
- `author.aliases` と `author.confirmed` は、この発注の範囲では**空配列と `false`** でよい。人確認台帳（`review/authors.yaml`）は別発注で作る。
- `reading.status` は、`異同確認.md` に読みの異同が記録されている首を `"review"`、それ以外を `"confirmed"` とする。判定根拠をコメントではなくコードで表現すること。
- `generatedOn` は**日付のみ**（`YYYY-MM-DD`）。時刻を出力しない。再現性が壊れるため。
- `dataVersion` は `paths.ts` に定数として置く。初版は `1`。

### 3.3 npm スクリプト

```
data:build   … 生成を実行する
data:check   … validate のみを実行する（CI 用）
test         … テストを実行する
```

テストランナーは **Node 標準の `node:test`** を使う。外部ランナーを入れないこと。TypeScript は `tsx` などの最小構成でよい。依存を増やさない方針を守ること。

## 4. validator が失敗として検出するもの

**この表が受入条件そのものである。** 各項目に対応するテストを書くこと。

| # | 検査 | 失敗時の意味 |
|---|---|---|
| V-01 | 3 ファイルとも番号 1〜100 が過不足なく 1 回ずつ | 転記漏れ・重複 |
| V-02 | 各行 7 列、空セルなし | 表の破損 |
| V-03 | 本文・歴史的・現代の 3 表で番号が一対一対応 | 参照切れ |
| V-04 | `異同確認.md` の判定値が本文一次データと一致（§5 の固定 fixture） | 正本が判定と食い違った |
| V-05 | `poems.json` の `text` が `ku[5]` の連結と一致 | 生成時の取りこぼし |
| V-06 | 読みが仮名（ひらがな・長音・小書き）以外を含まない | 読み欄への漢字混入 |
| V-11 | 同じ入力で 2 回生成した結果がバイト一致 | 再現性の喪失（順序・時刻の混入） |
| V-12 | `manifest.sourceHashes` が実ファイルの sha256 と一致 | 正本が生成後に変わった |
| V-14 | `generated/` に差分があるのに `data:build` を通していない | 生成物の手編集 |

V-07 / V-08 / V-09 / V-10 / V-13 / V-15 は人確認台帳（`review/*.yaml`）を前提とするため、**この発注の範囲外**である。実装しないこと。番号は欠番のまま維持し、後続発注で埋める。

## 6. 検証の進め方

`CONSTITUTION.md` §9 に従う。

1. 変更箇所の型検査
2. 対象 unit
3. 関連回帰

**正本変換は自動テストなしで変更しない。** テストは目的別に分けること。1 本の巨大なテストへ集約しない。

```
tests/data/parse.test.ts            表パーサの異常検出（列数・番号・空セル）
tests/data/validate.test.ts         V-01〜V-06, V-12
tests/data/reproducibility.test.ts  V-11, V-14
tests/data/variants-fixture.test.ts V-04（§5 の 10 件）
```

**検査が実際に効いていることを確認すること。** 壊した fixture を用意し、各検査がその fixture で失敗することをテストする。「常に通る検査」を書かないため。

## 7. 受入条件

1. `npm run data:build` を 2 回実行して生成物がバイト一致する。
2. 実行の前後で、一次資料 5 ファイルの sha256 が変わらない。
3. V-01〜V-06、V-11、V-12、V-14 のそれぞれについて、壊した fixture で失敗することをテストで示せる。
4. §5 の 10 件が fixture としてテストに入っている。
5. `generated/manifest.json` に `sourceHashes` と `counts` がある。`generatedOn` に時刻が含まれない。
6. 入出力パスがコード中に直書きされておらず、`paths.ts` に集約されている。
7. 外部依存が最小である（テストランナーは `node:test`）。

## 8. 停止して裁定を求める条件

次が起きたら実装を進めず、事実・影響・代替案を記録して報告すること。**回避策で埋めないこと。**

- 一次資料と `異同確認.md` の不一致を、根拠なしに一方へ潰す必要が生じた（計画 S-3）
- 100 首の番・本文・作者・読みの参照整合が取れない（計画 S-4）
- 再現性（V-11）を満たすために、出力から必要な情報を落とす必要が生じた
- 一次資料の書き換えなしには検査を通せない状況になった
