## 3. 設計

### 3.1 梯子（D-1・D-2）

段は `EventMethod` の1本の並びで表す。粒度は **新しい軸ではなく、梯子を何段下げるかという整数** である。

| 出題形態 | 下げ段数 | 自由入力で答えたときの段 | 上限 |
|---|---|---|---|
| 漢字だけ1つ（第2便） | 2 | `choice` | 65 |
| 文節1つ（第2便） | 1 | `kanji-to-kana` | 80 |
| 句1つ（現行） | 0 | `free-input` | 90 |
| **一首まるまる（第1便）** | — | **`whole-poem`（新設）** | **100** |

ヒント使用・部分正答は、そこからさらに1段下がる（現行の `effectiveMethodFor` のまま）。

**`compute.ts` に軸は1本も増えない。** 下げはイベントを作る時点で `effectiveMethod` へ焼き込まれる。
選び直しても過去の記録は動かない——「表示層にしか分岐が無い」状態にはならない。

**版は上げない。** 既存8段の `increment` / `cap` / `INCORRECT_DECREMENT` / `EARNED_POINTS` を
1つも変えず、段を **足すだけ** にする。よって過去のイベントの計算結果は1件も変わらず、
`MASTERY_RULES_VERSION` は 1 のまま据え置く。**全利用者の習熟度は保たれる。**

#### 新しい段の数値

```
MASTERY_RULES['whole-poem']         = { increment: 12, cap: 100 }
INCORRECT_DECREMENT['whole-poem']   = 5
EARNED_POINTS['whole-poem']         = 20
HINT_METHOD_DOWNGRADE['whole-poem'] = 'free-input'
```

- `increment: 12` — 5句を1度に書くので、句ごとの自由入力（+9）より上でなければ、
  難しいほうを選ぶと損になる。ただし90を超えた先は `OVER_NINETY_INCREMENT`（+2）が
  引き継ぐので、この値が効くのは89以下だけである。
- `INCORRECT_DECREMENT: 5` — **自由入力と同じに据え置く。上げない。**
  一首まるまるは5句のうち1句でも外すと×になるため、誤答の確率が構造的に高い。
  罰まで重くすると誰も挑戦しなくなる。
- `HINT_METHOD_DOWNGRADE: 'free-input'` — ヒントを使った一首まるまるは上限90で止まる。
  **100は無補助の一首まるまるだけが到達する。**

#### 100の条件を移す

```ts
export function isMasteryCompletionMethod(method: EventMethod): boolean {
  return method === 'whole-poem';
}
```

`rules.v1.ts:79` のコメントが「難度設定が入ったらこの関数の中身だけを差し替える」と
予告していた差し替えがこれである。

**`isRecallMethod` にも `whole-poem` を足す。** この関数は
`isMasteryCompletionMethod` の中身としてだけでなく、**`recommend.ts:69` から独立に呼ばれている。**
足し忘れると、一首まるまるを正解しても復習推薦が「まだ想起していない」と見なし続ける。
**赤くならない静かな穴なので、釘を立てる（N-W5）。**

### 3.2 一首まるまるをどう表現するか — **データを1件も増やさない**

既存の5つの `ku` 問題を **束ねて1問として出す。** 新しい問題データを生成しない。

- 束の識別子: `questionId = "pXXX-whole"`（合成。生成データには存在しない）
- `itemKey` は既存のまま `pXXX:text`
- 記録されるイベントは **1件**（`method: 'whole-poem'`）

**同一セッション内の繰り返し判定は、現行のまま `questionId` で行う。**
`compute.ts` の `seenQuestions` は `sessionId + questionId` で数えるので、
同じセッションで句3に答えたあと一首まるまるに答えても、識別子が違うため繰り返しにはならない。
**これは現行の規則どおりであり、変えない**（変えると既存の5句どうしの扱いも動く）。
ただし同じ束を同一セッションで2回出せば、`pXXX-whole` が一致するので増分は半分になる。

**新しい生成データを作らない理由:** 作ると、5句の `acceptedAnswers`（歴史的・現代の2通り）を
連結した全文の受理集合が要る。句ごとに2通りなら組み合わせは 2^5 = 32 通りで、
掛け算で増える受理集合は **正誤の正本を二重化する**。束ねれば、正誤の正本は既存の5件のままである。

`planQuestions` へ渡すために、束を `PublishedQuestion` 互換の値として **実行時に組み立てる**。
`blankUnit` に `'poem'` を足し、`prompt` は5つの空欄、`answer` は全文とする。
**この合成値は生成データへ書き出さない**（`questions.blank.json` は500件のまま）。

### 3.3 出現条件（D-3・D-4）

```
一首まるまるを候補に入れる ＝ 手動の段設定が「一首まるまる」
                        または  scores[`${poemId}:text`] >= MASTERY_RULES['free-input'].cap
```

**読む値は `scores[poemId + ':text']` であり、`poemMastery().score` ではない。**
後者は本文0.8＋作者0.2の重み付き点なので、本文を完璧に覚えていても作者問題に
一度も答えていない歌は72点にとどまり、**一首まるまるが永久に出ない。**
静かに間違える場所なので釘を立てる（N-W3）。

しきい値は `MASTERY_RULES['free-input'].cap` から引く。**90 と直書きしない**
（`entry.ts:84` のコメントが同じ理由を既に述べている）。

**降格も同型で許す。** 誤答で `:text` が90を割った歌では、一首まるまるは候補から外れる
（手動で上げている場合を除く）。作者問題の既存の裁定（2026-09-09）と同じ扱いである。

**D-3 の適用:** 自動は **歌ごとに上方向へだけ** 働く。手動で下の段にしている学習者には働かない。
手動で上げていれば、習熟度に関係なく出る。

### 3.4 採点

**句ごとに既存の `judge()` を5回呼ぶ。** `judge` は純関数で、束の5件はそれぞれ
自前の `acceptedAnswers` / `partialAnswers` / `normalization` を持っているので、そのまま使える。

- 5句すべてが `correct` → イベントの `judgement` は `correct`
- 1句でも `partial` があり、残りが `correct` → `partial`（現行どおり `effectiveMethod` が1段下がる）
- それ以外 → `incorrect`
- 画面には **句ごとの○×** を出す（どこを間違えたか分からないと学習にならない）

#### D-6: 5句にまたがる仮名遣いの混在は **△**（依頼者裁定・2026-09-13）

句1を歴史的、句2を現代で書いた場合、**束全体の判定を `partial` にする。**

**判定は安い。** 句ごとの `judge()` が○を返したとき、その答えが `answerHistorical` と
`answerModern` のどちらに一致したかを見るだけでよい。文字単位の解析は要らない。

- 5句すべてが○で、**採った綴りが全句で揃っている** → `correct`
- 5句すべてが○だが、**歴史的を採った句と現代を採った句が混ざっている** → `partial`
- **どちらとも数えない句**が2種類ある。いずれも仮名遣いの数え上げに加えない:
  1. `answerHistorical === answerModern` の句（そもそも違いが無い）
  2. **`answerHistorical` とも `answerModern` とも一致しない経路で○になった句**

**2 を落とすと誤判定する。** 発注（`260308a`・2026-09-10）で PDF 原本表記が正本になり、
**従来のMD表記が `acceptedAnswers` へ許容解答として入った。** たとえば `p005-blank-ku2` の
受理集合は `["もみぢふみわけ", "紅葉ふみ分け"]` で、後者は歴史的でも現代でもない**漢字表記**である。
これを「歴史的でも現代でもない＝混在」と数えると、**正しく答えた学習者が△になる。**
釘 N-W8 の fixture に、この経路で○になる句を1つ必ず入れること。

**この裁定には、既存の機構から自動的に出てくる帰結がある——混在した一首まるまるは100へ行けない。**
`partial` は `effectiveMethodFor()` で1段下がるので `whole-poem` → `free-input` となり、
上限が90に戻る。**点は入るが、100は綴りを揃えた者だけが取る。** 意図した設計であり、釘で留める（N-W8）。

**`mixed-kana-orthography.test.ts` は第1便では1行も変えない。** あの試験が見ているのは
**1つの語の中**での混在（生成データの整合）であって、句をまたぐ混在ではない。別の話である。

### 3.5 `delta` の削除（D-5）

`Event` から `delta` を落とし、`record.ts` の `deltaFor()` を消す。

**理由:** 試験以外のどこからも読まれておらず、しかも上限規則の **2つ目の写し** になっている。
段を足すと写しは3つ目・4つ目へ増える。読まれていない値の整合を保ち続ける理由がない。
既に `OVER_NINETY_INCREMENT` を知らずズレている（§2 の表）。

**保存済みイベントは書き換えない。** 余分なフィールドが残っていても `isEvent()` は通り、
`compute` は `delta` を読まないので、計算結果は変わらない。**移行処理は不要である。**

## 6. 破壊試験（**1件の破壊が1本だけ赤くする** こと）

**感度と特異度を対で測る。** 各行について「何が赤くなるか」を先に書き、実行して確かめる。
**全部赤くなる破壊は別の欠陥を叩いている。** 破壊のあとは `cp` で復元する
（Python の書き戻しは改行が化け、ハッシュがずれる）。**各実行に時間上限を付ける**——
壊し方によっては赤ではなく終わらないことがある。

| # | 壊すもの | 赤くなるべき釘 | 赤くなってはいけないもの |
|---|---|---|---|
| M-1 | `isMasteryCompletionMethod` を `isRecallMethod` へ戻す | N-W6 のみ | 他すべて |
| M-2 | `isRecallMethod` から `whole-poem` を抜く | N-W5 のみ | N-W6 |
| M-3 | しきい値を `poemMastery().score` から引くよう変える | N-W3 のみ | 他すべて |
| M-4 | しきい値の `>=` を `>` にする | N-W3 のみ | 他すべて |
| M-5 | 手動設定の参照を消す | N-W4 のみ | N-W3 |
| M-6 | `MASTERY_RULES['free-input'].cap` を 80 へ変える | N-W1 と N-W3 | — |
| M-7 | 束の判定を「1句でも正解なら○」へ変える | N-W7 のみ | 他すべて |
| M-8 | `whole-poem` の `cap` を 90 にする | N-W6 のみ | 他すべて |
| M-9 | 混在の判定を消す（混ざっていても `correct` を返す） | N-W8 のみ | N-W7 |
| M-10 | 混在の判定を逆にする（揃っていると `partial`） | N-W8 のみ | 他すべて |

**N-W8 の fixture は、`answerHistorical !== answerModern` の句を2つ以上含めること。**
両方が同じ綴りの句ばかりで束を作ると、「混ざっている」という状態が存在しないので、
**判定を消しても緑のまま**になる（M-9 が当たらない）。fixture は生成データそのものを使わず、
2つの実装を区別できる値を手で置く。

**M-2 が N-W6 を赤くしてしまう場合、`isMasteryCompletionMethod` が `isRecallMethod` を
呼び返している。** §3.1 の書き方（`method === 'whole-poem'` を直接書く）にすると分離できる。

**M-6 は2本赤くなることを意図している。** 上限を動かすと出題側も一緒に動くのが
§3.3 の設計なので、片方だけ赤いなら直書きが残っている。

**破壊が当たっているか（置換件数が0でないか）を毎回確かめること。** 赤くならない緑は証拠ではない。

## 7. 停止条件

1. **`isMasteryCompletionMethod` の差し替えと、一首まるまるの出題は、同じ便から出す。**
   分けると、100の条件が移った後に一首まるまるが出せず、**誰も100へ行けない期間** ができる。
2. **5句の連結が全文と一致しない首が1首でも出たら止める。** 落とさない。差分を勝手に埋めない。

4. **§4 の一覧に無いファイルを変える必要が生じたら止める。**
5. **破壊試験で「全部赤」または「全部緑」が出たら止める。** 釘が効いていないか、別の欠陥を叩いている。
6. **作業ツリーに残る他の作業者の未コミット3ファイルに触れない**
   （`docs/CODEX_HANDOFF.md`・`docs/HANDOFF.md`・`古典関係アプリ_設計計画書_2026-08-29.md`）。

## 9. 別便へ送った件: 語の中の混在を×から△へ（D-7）

**時期の条件は「読み」のPDF照合のあと。本文表記の照合ではない**（済んでいる。下記）。

**依頼者は「やる」と裁定した。時期だけ PDF 照合のあとへ送った。**
次に着手する人が測り直さずに済むよう、調べた結果をここに置く。

### 延期した理由

**ここでいう照合は「読み」のPDF照合である。「本文表記」の照合とは別である。**

- **本文表記のPDF照合は済んでいる**（`260308a` / `792d3c5`・2026-09-10）。
  75首・127件。PDF原本表記を表示の正本にし、従来のMD表記を許容解答として残した。
  台帳は `百人一首_本文校正一覧_PDF原本表記_許容解答.md`、釘は `tests/data/pdf-text-corrections.test.ts`。
  **台帳自身が「本文のみ。作者名・作者読みは扱わない」と明記している。**
- **読み2ファイルは1文字も変わっていない。** 最後に変わったのは `6ff4b5c`（97番の読みを訂正）。
  `review/readings.yaml` は **100首とも `pending` のまま**である。

**本文側の反映は、一部の検収を飛ばして実装している**（依頼者判断・2026-09-10）。
既に公開済みの内容の誤りであり、訂正を急ぐ必要があったためである。
**読みの照合に着手する人は、本文側にも未検収部分が残っている前提で扱うこと。**
（この事情は公開物である台帳には書かない。台帳には反映済みであることだけを書いた。）

`mixed-kana-orthography.test.ts` は、**読み2ファイル**を直す作業の見張り役である。
×→△にすると、この試験の `assert.equal(..., 'incorrect')` を `'partial'` へ書き換えることになり、
**照合作業の基準線を、照合の直前に動かす**ことになる。

（試験そのものが死ぬわけではない。正規化が ぢ/じ を潰せば混在は `partial` ではなく
`correct` になるので、`partial` を期待する assert でも赤くなる。死ぬのは基準線のほうである。）

### 測った事実（2026-09-13）

| | 全件 | 歴史的＝現代 | 1文字違い | 長さ違い | **混在が成立する** |
|---|---|---|---|---|---|
| 本文 | 500 | 321 | 146 | 4 | **29件（5.8%）** |
| 作者（free） | 100 | 35 | 26 | 13 | **26件** |

**1文字しか違わない語には「混在」という状態が存在しない。** 片方の字を採れば、もう一方の綴りになるだけである。
既存試験の `hybrid()` が `differing.length < 2` を弾いているのは同じ理由である。

### 実装の道は1本しかない

**混在の綴りを生成データへ焼く道は破綻する。** `p083-author-free`（皇太后宮大夫俊成）は
歴史的 `くわうたいごうぐうのだいぶとしなり` と現代 `こうたいごうぐうのだいぶしゅんぜい` が
**17文字違う**——これは仮名遣いの差ではなく読み方そのものが別（俊成／しゅんぜい）である。
この1語だけで 2^17 − 2 = **131,070通り** 必要になる。

よって **`judge()` に文字単位の構造判定を足す**しかない。**正誤判定の正本に手を入れる作業である。**

### `百人一首_読み_歴史的仮名遣い_作者訂正版_v2.md` について（2026-09-13 に素性を確認）

依頼者が Codex との作業で作った作業データ。**採用されていないが、中身は既に効いている。**

正本 `百人一首_読み_歴史的仮名遣い.md` と突き合わせた結果（実測）:

| | 差 |
|---|---|
| 本文読み（500句） | **0件** |
| 作者読み | **3件のみ** — 61・89・97 |

| # | 正本 | v2 |
|---|---|---|
| 61 伊勢大輔 | `いせのたいふ` | `いせのおほすけ` |

**この3件はすべて、既に出荷済みデータの `acceptedAnswers` に入っている。**
`review/authors.yaml` で `alsoAccepted` として `status: approved`（batch・`docs/H04_BATCH_EVIDENCE.md`）に
なっており、生成データへ流れている。たとえば `p097-author-free` の受理集合は
`ごんちゆうなごんさだいへ` と `ごんちゆうなごんさだいえ` を含む。**学習者は既にどちらで答えても○である。**

v2 を採用すると変わるのは **どちらを「主」にするか** だけであって、受理の範囲は変わらない。
**急いで採用する理由はない。**

**採用するなら、89 の行はそのまま使えない。** 値のセルに `（異読：しきしないしんわう）` という
注記が埋め込まれている。**そのまま取り込むと、読みに丸括弧が入る。**

**あわせて見つかった矛盾（読みの照合で直す候補）:** 正本 `百人一首_読み_歴史的仮名遣い.md` の
**第122行の注記は「本表は `いせのおほすけ` を採用した」と書いているが、表の第61行は `いせのたいふ` である。**
文と表が食い違っている。v2 は表のほうを注記に合わせたものと読める。

### 着手する人への注意

- **本文では、統一すると「現代仮名遣いで揃えて書いた」と「取り混ぜた」が区別できなくなる。**
  現代は D-26 で既に △ であり、`Judgement` は 4 値しかないので、あいだに段を作れない。

## 10. 検収について

**実装と検収を同じ者が行うと、証明力が落ちる。** Codex が使えないあいだの埋め合わせとして:

- **実装セッションと検収セッションを分ける。**
- 検収側は **報告の数値を1つも転記せず、全部再実行する。**
- §6 の破壊試験を **反転し直す**（「赤くなるべき」と書いてあることを信じない）。
- **追加した検査を実際に完走させたか** を確かめる。過去に「追加した」報告が未実行だった例がある。
- **検収が終わるまで、依存・実行環境を片付けない。**
