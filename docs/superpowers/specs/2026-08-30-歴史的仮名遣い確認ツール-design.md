# 歴史的仮名遣い確認ツール 設計書

作成日: 2026-08-30
状態: 設計確定（実装計画は未作成）

## 1. 目的と位置づけ

歴史的仮名遣いで書かれた語を、現代仮名遣いへ直す練習をするための公開Webツールである。学習者はかなで答えを入力し、完全一致で採点される。誤答時は、どの規則の適用で止まったかを機械的に診断して返す。

古典学習帳（百人一首アプリ）とは**同一リポジトリ内の並行プロダクト**とする。`CONSTITUTION.md`、`docs/DESIGN_SYSTEM.md`、習熟度モデル、保存スキーマを共有し、公開単位とデータだけを分ける。百人一首アプリからリンクしてよいが、単独で成立させる。分離が必要になった時点で別リポジトリへ切り出す。

**裁定 D-06（2026-08-30、採択）により構成が確定した**（`docs/ADR/0004-two-products-layout.md`）。公開リポジトリは1つとし、共有層 `packages/shared` の下に公開単位 `packages/hyakunin` と `packages/kanazukai` を置く。GitHub Pages の別パス（`/hyakunin/`、`/kanazukai/`）で2つを配信する。本ツールは `packages/kanazukai` である。

同 ADR の**裁定 D-01** が習熟度の蓄積単位を定めており、本設計書の第6.0節・第8節はこれに従う。

本ツールが扱うのは**表記の変換**であり、発音の再現ではない。この区別は第3節で規則として定義し、第5節で採点仕様に反映する。

### 1.1 初回公開に含むもの

- 13規則にもとづく単語の出題と、かな入力による完全一致採点
- 誤答の規則単位診断
- 段階的ヒント（語義・漢字・規則名・答え）
- 習熟度の算出と本人向け表示
- 3モード（通し練習・規則別・まちがい直し）
- 端末内保存、JSONの書き出し・読み込み・重複排除マージ
- 問題報告

### 1.2 初回公開に含まないもの

- 句・短文の出題（規則 `H1-c`・`W2-a` はこのとき有効になる）
- 匿名統計（イベント構造は適合させておき、後から有効化する）
- 紙・手書き想起
- クラウド同期、ログイン
- 選択式・漢字候補形式の出題

## 2. 用語

- **語 (`wordId`)**: 出題の対象となる一語。歴史的仮名遣いの表記を主キー相当の識別に用いず、安定IDを別に持つ。
- **規則 (`ruleId`)**: 変換規則。`H1`、`L3` のように表す。
- **問 (`questionId`)**: 一つの出題インスタンス。語とモードの組。
- **回 (`sessionId`)**: 一回の学習開始から結果表示まで。
- **日**: 利用端末のローカル日付（`YYYY-MM-DD`）。

## 3. 仮名遣い変換規則

### 3.1 規則の向きについて

参照した資料は、いずれも本ツールが必要とする向きでは書かれていない。

| 資料 | 記述の向き |
|---|---|
| 古典文法教材 | 歴史的表記 → **音** |
| 内閣告示「現代仮名遣い」 | 現代語の**音** → 現代の表記 |
| **本ツール** | **歴史的表記 → 現代の表記** |

この差を意識せずに片方から写すと、偽の規則が混入する。実例として、内閣告示第2の「オ列の仮名に『お』を添えて書く」語群（`こおり`・`とお`・`おおかみ`・`ほのお`・`いきどおる`）を独立規則として立てかけたが、検算の結果すべて `H1`（ハ行転呼）と `W2`（を→お）だけで正しく導出でき、独立規則ではないと判明した。告示がこれを特例としているのは、告示が現代語の音から出発しているためである。

### 3.3 長音3規則の表記について

`L1`・`L2`・`L3` だけローマ字表記を用いる。仮名では記述できないためである。

| 歴史的 | 実際の変化 | 仮名だけの説明 |
|---|---|---|
| か\|う | k \| au → k \| ō | 「オ段＋う」で通る |
| け\|う | k \| eu → k \| yō | 「拗音ょ＋う」で通る |
| **せ\|う** | **s \| eu → s \| yō** | **せ が しょ になる理由を言えない** |
| て\|う | t \| eu → t \| yō | て が ちょ になる理由を言えない |

`せ`・`て` で破綻するのは、訓令式で `si`・`ti` だからである。子音は保存され母音だけが変わる規則だが、仮名は子音を単独で表記できない。したがってローマ字は代替表記ではなく、この規則の唯一の正確な表記である。

チップにはマクロン表記（`au→ō`）を用いる。学習者の手元にある教材と一致させるため。展開時に、実際に書く仮名（`おう`・`ゅう`・`ょう`）を併記する。音の表記と仮名の表記は役割が異なるため、両方を示す。

## 4. データ設計

`CONSTITUTION.md` 第3条に従い、Markdown を正本、JSON を再生成可能な派生物とする。

### 4.1 `仮名遣い規則_一次データ.md`

第3.2節の規則表そのもの。列は `規則ID / チップ表示 / 説明 / 代表例 / 典拠 / 出題対象 / 親規則ID`。規則を修正したとき、`適用規則` 経由でどの語の解説が変わるかを追跡できる。

### 4.2 `仮名遣い語彙_一次データ.md`

| 列 | 用途 | 例 |
|---|---|---|
| `id` | 安定ID | `k0042` |
| `歴史的仮名遣い` | 出題文字列（ひらがなのみ） | `てうづ` |
| `現代仮名遣い` | 主正解 | `ちょうず` |
| `許容正解` | 複数正解がある語のみ | （空） |
| `漢字` | ヒント（任意） | `手水` |
| `語義` | ヒント・解説（短く） | `手や口を清める水` |
| `適用規則` | 規則IDの配列 | `L3, D1` |
| `難度` | `単独` / `複合` | `複合` |
| `分類` | `日常語` / `入試重要古語` / `百人一首由来` / `現代仮名遣い例外` | `入試重要古語` |
| `混同注意` | 誤答パターンのタグ | `オ列長音` |
| `確認状態` | `未確認` / `照合済み` / `要再確認` | `照合済み` |
| `典拠` | 照合した資料 | `画像①⑤, 告示第2` |

「変化なし」語に独立列を設けず、`歴史的仮名遣い == 現代仮名遣い` で判定する。列を減らして矛盾の余地を消すため。

### 4.3 複数正解の扱い

内閣告示第2は、二語の連合による ぢ・づ のうち現代語で二語に分解しにくいものについて、「じ・ず」を本則とし「ぢ・づ」を許容とする（`いなずま／いなづま`、`せかいじゅう／せかいぢゅう`、`かたず／かたづ`）。完全一致採点でこれを出題すると正しい答えを不正解にする。

- `許容正解` 列を最初から用意し、採点は `主正解 ∪ 許容正解` との照合とする。後から列を足す改修を避ける。
- v1 では許容併記語を出題対象から外す。「どちらでもよい」は完全一致練習の趣旨に合わない。データには残すため、方針を変えれば有効化できる。
- 同じ理由で `給ふ`（たまう／たもう）も出題しない。

## 5. 採点と誤答診断

### 5.1 入力の正規化

判定前に次を適用する。

| 処理 | 理由 |
|---|---|
| Unicode NFC 正規化 | iOS の一部入力で `が` が `か`＋結合濁点になり、見た目が同じでも不一致になる |
| カタカナ → ひらがな | 表記種別の違いで落とさない |
| 前後の空白除去 | 入力事故 |
| 長音符「ー」は正規化**しない** | 下記のとおり誤りとして扱う |

長音符を残すのは意図的である。教材は答えを「チョーズ」と発音で示すため、学習者が `ちょーず` と書くのは、規則を理解したうえで表記に落とす段を踏んでいない状態を示す。これを正解にすると、本ツールが固有に教えられる部分を捨てることになる。不正解としたうえで「発音はそのとおり。現代仮名遣いの表記に直すと」と返す。

### 5.2 誤答診断

語ごとに `適用規則` を持つため、規則の部分適用をすべて生成して入力と突き合わせることで、どの規則で止まったかを特定できる。`てうづ`（正解 `ちょうず`、適用規則 `L3`・`D1`）の例：

| 入力 | 生成元 | 返す内容 |
|---|---|---|
| `てうづ` | 無適用 | まだ直っていない |
| `ちょうづ` | `L3` のみ | ぢ・づ の直しが残っている（`D1`） |
| `てうず` | `D1` のみ | エ段＋う の長音化が残っている（`L3`） |
| `ちょうず` | `L3`+`D1` | 正解 |

過剰適用は、誤答生成規則から逆引きする。誤答生成規則は次の5つに限定し、これ以外は「該当なし」として正解のみを示す。診断できない誤りに憶測の説明を付けない。

| # | 誤答生成規則 | 入力例 | 正解 | 返す内容 |
|---|---|---|---|---|
| E1 | オ列長音を「う」で書く | `こうり` | `こおり` | `H1` の後に書き換えすぎ。`あふぎ→おうぎ` と対比する |
| E2 | `D1` を `D1-a` 語へ適用 | `つずく` | `つづく` | 同音の連呼はそのまま |
| E3 | `S1` 未適用（拗音・促音を大書き） | `ちようず` | `ちょうず` | 拗音は小さく書く |
| E4 | 長音符「ー」の使用 | `ちょーず` | `ちょうず` | 発音では正解。表記に直す段が残っている |
| E5 | `H1` を語頭・複合語後部要素へ適用 | `わつはな` | `はつはな` | 語頭のハ行は変えない |

すべて決定的な規則処理で行い、生成AIを用いない。`CONSTITUTION.md` 第3条「生成AIを正解判定の根拠にしない」を設計段階で満たす。

### 5.3 診断結果の用途

診断結果は**加点に反映せず、出題選択に用いる**。`LEARNING_SCIENCE_AUDIT.md` が既存係数を「試験運用で校正する設計係数」と位置づけている以上、独自係数を足すと校正対象が二重になるため。

イベントに `missedRules: ["D1"]` を記録し、推薦の優先順に反映する。百人一首アプリの推薦は歌単位だが、本ツールは**規則単位で推薦できる**。「ぢ・づ で3回つまずいています」と規則を名指しし、その規則の語を集めて出す。

### 5.4 入力欄の実装要件

- 送信は独立したボタンとし、Enter を送信に割り当てない。日本語IMEでは Enter が変換確定に食われるため。
- `compositionend` を待って値を読み、未確定文字列で採点しない。
- 変換せずひらがなのまま送れることを、最初の1問で明示する。
- ラベル、入力例、エラー位置を付ける（`CONSTITUTION.md` 第8条）。

## 6. 習熟度モデル

`docs/APP_SPEC.md` §8 および `docs/LEARNING_SCIENCE_AUDIT.md` の係数を流用する。**新しい数値を導入しない。**

百人一首アプリの「方式」の軸は *閲覧→自己評価→選択式→漢字候補→自由入力* だが、本ツールは自由入力に一本化されている。代わりに**ヒント段階を方式の軸に読み替える**ことで、既存係数がそのまま適用できる。

| 本ツールのイベント | 百人一首の対応 | 増分 | 上限 |
|---|---|---:|---:|
| ヒントなしで正答 | 自由入力正答 | +9 | 90 |
| ヒント1つの後に正答 | 漢字候補→ひらがな | +7 | 80 |
| ヒント2つ以上／規則名を見て正答 | 選択式正答 | +5 | 65 |
| 答えを表示した | 閲覧 | +1 | 20 |
| 誤答（ヒントなし） | 自由入力の誤答 | −5 | 0未満にしない |
| 誤答（ヒント後） | ヒント後の誤答 | −3 | 0未満にしない |

適用規則も百人一首アプリと同一とする。

- 同一回に同じ問題へ再回答した場合、2回目以降の加点は半分。
- 90を超えるには、**別の日**のヒントなし正答を要する。表示上限は100。
- 時間経過だけで％を下げず、「そろそろ確認」を別に表示する。
- 上限適用後に総合値を 0〜100 に収める。

### 6.0 蓄積単位（裁定 D-01）

**`itemKey = wordId` とする。** `docs/ADR/0004-two-products-layout.md`（裁定 D-01）による。

本設計書の初版は §6 で「`語ID × 出題形式`」、§8 で「`wordId × rule`」と書いており食い違っていた。`wordId × rule` を蓄積単位にすると、`てふ`（`H1`＋`L3`）のように複数規則が絡む語で1回の正答が複数キーへ加点され、`docs/APP_SPEC.md` §8 の上限表と「同一回の再回答は加点半分」の算術が壊れる。**規則は1つの答案から診断される属性であって、別の想起行為ではない。** したがって蓄積単位は問の単位（＝語）に置き、規則は分析次元へ降ろす。

本ツールは出題形式を自由入力に一本化しているため、百人一首アプリの `skill` に相当する第二の軸を持たない。

規則（`ruleId`）は**習熟度の加点対象にしない**。`Event` に診断された `ruleId` の配列を分析用キーとして持たせ、推薦・規則別モード・「誤答が集中している規則」の集計に用いる（第5.3節）。

### 6.1 表示

習熟度は**語単位**で表示する（`itemKey` 単位ではない）。能力・評定・記憶確率・他者比較とは表示しない。％、メーター、5色（灰・赤・黄・青・緑）を併用し、色だけに依存させない。境界は未着手=灰、1〜29%=赤、30〜59%=黄、60〜84%=青、85〜100%=緑とする。

本ツールでは `itemKey = wordId` であるため蓄積単位と表示単位が一致するが、百人一首アプリ（蓄積は `poemId × skill`、表示は首単位）と規則を揃えるため、単位を明示して実装する。

### 6.1 推薦

次に確認する一件を、次の順で選ぶ。利用者は終了、別範囲、モード変更を選べる。

1. 期限を過ぎた語で、別日の想起が未達のもの
2. **誤答が集中している規則**の語（本ツール固有）
3. 誤答・答え表示が直近にあるもの
4. まだ別セッションでの想起成功がないもの
5. 正解済みだが一定期間再確認していないもの

同点時は安定した順序とする。毎回ランダムにして「学習済み」と錯覚させない。推薦理由を短く示す。

## 7. 画面と操作

### 7.1 縦書き・横書き

**単語モードは横書きとする。** `CONSTITUTION.md` 第7条は「本文と回答対象は縦書き」と定めるが、これは百人一首の歌を想定した規定である。単語1語では縦書きにしても読みやすさの利得がなく、入力欄との視線移動が増えるだけであるため。

第7条に「単語単位の出題は横書きとする」を追記する（第12節を参照）。将来 句・短文モードを追加する場合は、そのモードだけ縦書きで設計する。

### 7.2 ヒントの段階

「わからない」を押すと段階的に開く。開くほど習熟度への寄与が下がる。

1. 語義（`手や口を清める水`）
2. 漢字（`手水`）
3. 規則名（`eu→yō`／`ぢづ→じず`）— 規則名のみを示し、答えは出さない
4. 答えと解説

### 7.3 モード

ホームの第一操作は「とりあえず始める」とする（`CONSTITUTION.md` 第7条）。1セット20問。

- **通し練習** — 全語からランダム
- **規則別** — 規則を選んで集中
- **まちがい直し** — 誤答した語のみ

URLパラメータは `?rule=L3`、`?set=日常語` とする。百人一首アプリの `?from=&to=` は1〜100の連番を前提とする仕組みであり、語彙には適用できない。

### 7.4 デザイン

`docs/DESIGN_SYSTEM.md` を全面採用する。Zen Maru Gothic / Klee One の self-host、OKLCH トークン、4pt 余白スケール、操作部品の8状態、320/375/414/768px のレスポンシブ契約、禁止事項。出題語の表示に Klee One、UI に Zen Maru Gothic を用いる。

### 7.5 問題報告

各問に「問題を報告」を置く。仮名遣いデータは誤りが混入しやすいため v1 必須とする。語ID・データ版・アプリ版を自動添付し、氏名・連絡先の入力欄は置かない。

## 8. 保存・書き出し

`docs/APP_SPEC.md` §9 のスキーマを共通化する。

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-08-30",
  "deviceId": "random-local-id",
  "settings": {},
  "sessions": [],
  "events": [],
  "reports": []
}
```

`events` の `itemKey` のみ、百人一首アプリが `poemId × skill`、**本ツールが `wordId`** として使い分ける（裁定 D-01、第6.0節）。同じ書き出しファイルで両方の履歴を運べるため、将来の統合が改修ではなく設定になる。

裁定 D-06 により、`Event` は `product` を持ち、IndexedDB は1 DB に統一して `events` ストアに `product` インデックスを置く。初期化はプロダクト単位で選べるようにする。書き出し形式への `product` 判別子追加と `schemaVersion` を2へ上げるかは **H-13** として未決であり、P4（保存・移行）の着手までに決める。

- IndexedDB を第一候補、不可の場合 LocalStorage へフォールバック。
- 各イベントを書き込んだ後に画面を進める。
- 読み込みは既存記録を消さず、`eventId` の同一値を重複として一回だけ採用する。
- 習熟度は保存値を上書きせず、イベントから再計算する。
- 初期化は習熟度・回答・履歴を対象とし、表示設定は残す。対象と件数を明示した確認を必須とする。

匿名統計は v1 では実装しないが、イベント構造を `docs/APP_SPEC.md` §11 に適合させ、後から有効化できる形にする。

## 9. データ収集計画

### 9.1 規模

規則語と例外語を分けて数える。例外の扱いは第9.5節による。

| 段階 | 規則語 | 例外語 | 達成条件 |
|---|---:|---:|---|
| v0 | 60 | **0** | 出題対象13規則を単独3例（39語）＋複合2例（約20語）。例外は含めない |
| **v1** | **180** | **20** | 分類別目標（下表）を充足、「変化なし」語15〜20% |
| v2 | 360 | 40 | 入試重要語の網羅 |
| v3 | 700〜900 | 80〜100 | 日常語・派生形の拡張。以降は語彙アプリの領域 |

語数ではなく**規則カバレッジ**を達成条件とする。`適用規則` を配列で持つため、「`H1` の例が足りない」「`L3`×`D1` の複合が1例しかない」といった穴をクエリで検出でき、収集作業に終わりを定義できる。

1000語は規則習得への寄与がほぼ頭打ちになる上限であり、目標として持つが v1 の条件にはしない。律速は生成ではなく人による照合（1語2〜3分）である。

### 9.2 供給源（v1=200語の内訳）

| 供給源 | 語数 | 性格 |
|---|---:|---|
| 現代語にも残る日常語 | 70 | `かは→かわ`、`こひ→こい`、`をんな→おんな`。学習の入口として最重要 |
| 入試重要古語 | 80 | 複数の単語帳・古語辞典に共通して載る語を、規則カバレッジ基準で選び直す。古典教材の定番作品（竹取・伊勢・土佐日記・枕草子・徒然草）の頻出語を含む |
| 百人一首由来 | 30 | 既存対訳から抽出。出典が明確で照合コストが低い |
| **（合計 規則語）** | **180** | |
| 例外語（別扱い・第9.5節） | 20 | 内閣告示第2の `つづく`・`ちぢむ`・`みかづき` 群、および P1c で発見される `はは` 型の語彙的例外 |

横断タグ「変化なし」を全体の15〜20%（30〜40語）確保する。上記4分類の内数。「変化なし」語を入れないと、学習者が「何か変えれば当たる」という誤った戦略を覚えるため。多すぎると練習にならないので比率を固定する。

添付資料の練習問題にあった `ひとごゑ`・`かはづ`・`をりふし`・`たふとし`・`いへぢ`・`てうづ` は初期セットに含める。

**単語帳からの選定について。** 特定の単語帳の収録語と配列をそのまま写すと編集著作物の複製になりうる。複数の資料に共通して載る語だけを規則カバレッジ基準で選び直し、各語の `典拠` 列に照合資料を残す。

### 9.3 採らない語

- 正解が割れる語（許容併記、慣用読み）
- 固有名詞
- 現代語として意味が取れず、仮名遣い以外の負荷が高すぎる語
- **仮名だけでは語を特定できない語**（下記）

`K1`（合拗音）の語には固有の問題がある。`くわし` は 菓子（`K1` を適用して `かし`）とも 詳し（歴史的 `くはし`、`H1` を適用して `くわし` のまま）とも読め、**仮名表記だけでは正解が定まらない**。

`K1` の出題語は、次のいずれかを満たすものに限る。

- 仮名表記が一意に定まる語を選ぶ
- または、語義・漢字ヒントを最初から表示した状態で出題する（この場合の習熟度はヒント1つ相当として扱う）

同種の同綴異義は `K1` 以外でも起こりうるため、P4 の照合時に「この仮名表記で他に読める語がないか」を確認項目に含める。

### 9.4 百人一首データによる規則表の検証

既存の `百人一首_読み_歴史的仮名遣い.md` と `百人一首_読み_現代仮名遣い.md` は、100首×5句＋作者名の対訳が照合済みで揃っている。ここにコンバータをかけて既存の現代仮名遣い列と突き合わせることで、**約600件の実データで規則表を検証できる**。

不一致は「規則表の穴」か「百人一首データの誤り」のいずれかであり、どちらも発見である。両プロダクトの品質が同時に上がるため、同一リポジトリとする根拠がここで具体化する。

この工程は語の収集ではなく規則表の検証であり、**語を集める前に実施する**。穴のある規則表で60語作ると全部やり直しになるため。

### 9.5 例外語の扱い

例外語は規則語と分離し、独立した区分として管理する。出題の順序・比率・習熟度への影響を、規則語とは別に定める。

#### 根拠

**Heffernan, Schlichting & Mack (2021)** は、「規則に従う項目＋例外」構造のカテゴリー学習課題で、例外を提示するタイミングを操作した。例外を学習ブロック1から提示する条件（Early）と、ブロック2以降に遅らせる条件（Delayed）を比較し、**遅らせた条件で例外の分類精度が有意に高かった**。解釈は、先に規則項目だけに触れることで規則の抽象表象が形成され、その後に例外が来ると不一致信号が生じてパターン分離が働き、例外が別個に符号化されるというものである。刺激構成は1カテゴリーあたり プロトタイプ4・規則項目4・例外2 で、学習ブロックではプロトタイプが他の2倍の頻度で提示された。提示回数ベースで例外は約14%にあたる。

**Taylor & Rohrer (2010)** は、児童に4種類の算数問題を交互（`abcbcacab`）またはブロック（`aaabbbccc`）で練習させた。交互練習は練習中の成績を下げたが、翌日のテストでは得点がほぼ倍になった。誤答分析では、ブロック条件の誤りの多くが「別の種類の問題の解法を選ぶ」ものであり、交互練習が伸ばすのは**どの規則を当てるかを選ぶ力**である。

**限界。** 前者は成人の人工的カテゴリー学習課題（刺激10個）、後者は児童の算数である。日本語の仮名遣い規則や中高生への直接の根拠ではない。以下は設計判断であり、効果の保証ではない。`LEARNING_SCIENCE_AUDIT.md` と同じ基準で、試験運用により校正する。

#### 設計

| 決定 | 根拠 |
|---|---|
| v0（60語）に例外を含めない | 規則の抽象化を先に作る（Heffernan et al. 2021） |
| 例外は**親規則の規則到達度が60以上**になってから出題キューに入る | 「Delayed 条件」の実装。60 は `DESIGN_SYSTEM.md` の5色境界（青の下限）に合わせた設計値 |
| 例外の出題比率は全体の10〜15%を上限 | 実験の提示比率（約14%）を参照した設計値 |
| 規則語は規則をまたいで交互に出す。規則別モードは選択制で既定にしない | Taylor & Rohrer (2010) |
| 例外語は**規則到達度の計算に含めない** | 例外の誤答で規則到達度が下がると、規則の学習が例外に汚染される。構造の決定であり新しい係数を導入しない |

**規則到達度の定義。** 裁定 D-01 により規則は習熟度の加点対象ではないため、「親規則の習熟度」という量は存在しない。代わりに次の派生値を定義する。

> **規則到達度**（規則 `R`）＝ `適用規則` に `R` を含む**規則語**の習熟度の平均。例外語（`分類=例外`）は計算に含めない。

これは分析用の派生値であり、加点対象の指標ではない。イベントから毎回再計算し、保存値を持たない。第5.3節の「誤答が集中している規則」の集計、第7.3節の規則別モード、および例外の解禁判定に用いる。

#### 動機づけへの配慮

Taylor & Rohrer で交互練習は**練習中の成績を下げた**。効いている設計ほどその場の手応えは悪く、例外を加えるとさらに悪化する。次を仕様とする。

1. **練習中の正答率を主要な数値として表示しない。** 別日想起を重く扱う習熟度％を主指標とする（`CONSTITUTION.md` 第2条の圧力を設けない方針と同方向）
2. **例外を「規則の失敗」ではなく別種の対象として枠づける。** 覚えるべき追加規則ではなく、集めて眺める一覧として提示する。これは枠づけの選択であり、動機づけ効果を主張する根拠は持たない。未検証として記録する
3. **代表例外を先に出す。** `はは`（母）・`つづく`・`ちぢむ`・`こおり` のように、現代語でも使い、見れば納得できるものから導入する。規則を知らなくても納得できる例外は、規則への信頼を壊さない

#### データ上の区別

例外語は `分類=例外` とし、次の列を追加で持つ。

| 列 | 用途 | 例 |
|---|---|---|
| `親規則` | 破っている規則 | `D1` |
| `例外の型` | `告示による例外` / `語彙的例外` | `告示による例外` |
| `通常なら` | 規則を適用した場合の（誤った）結果 | `つずく` |

`通常なら` 列があることで、「通常 `ぢづ→じず` だが、この語は違う」という形の解説を自動生成できる。第5.2節の誤答診断 E2 の説明文もこの列から作る。

## 10. 実装分担

### 10.1 原則

> 仕様が文章で確定している作業は Codex。仕様を決める作業と、仕様どおりかを判定する作業は Claude。
> 受入テストは実装者ではなく検収者が先に書く。

実装者が自らテストを書くと実装の挙動に合わせたテストになり、バグごと固定される。コンバータと習熟度エンジンは期待値を先に書ける種類の処理であるため、この分離が有効である。

### 10.2 モデル層の選択基準

**上位方針は `docs/HANDOFF.md` §10 である。** 本節はそれを本ツールへ適用したものであり、矛盾する場合は HANDOFF を優先する。

Codex は GPT-5.6 の3層（Sol / Terra / Luna）を用いる。価格は100万トークンあたり Sol $5/$30、Terra $2.50/$15、Luna $1/$6。

HANDOFF §10.1 の定めにより、**Codex へ Sol は原則として使わない。** 判断は Claude 側と人が持ち、Codex へ発注する時点で仕様は確定しているべきであるため。Sol を使いたくなった場合、それはモデル層の問題ではなく発注文書の記述が足りていない兆候として扱い、仕様を詰めて Terra で足りる形に直す。

したがって層の選択基準は次となる。

> **受入条件が機械判定できる作業は Terra。パターン照合のみは Luna。機械判定できない作業は Codex へ出さず、Claude と人が持つ。**

「テストで検出できない作業を Sol に投げる」という選択肢を置かないことが要点である。検出できない誤りは、モデルを上げても検出されない。

CodeRabbit のベンチマークとして紹介されている値では、Sol の成功率 63.7%（平均 20,968トークン）に対し Terra は 40.7%（55,594トークン）であり、安い層の方がトークンを多く使い成功率が低い。ひとつのベンチマークであり鵜呑みにはできないが、示唆は「安い層を避けよ」ではなく **「Terra が一度で通る程度に仕様を詰めよ」** である。T2・T7 で Claude が受入テストを先に書く設計は、この目的にも資する。

Claude 側は Opus 5 / Sonnet 5 / Haiku 4.5 を用い、強度は low / medium / high / xhigh / max で指定する。

### 10.4 失敗時の対応

`HANDOFF.md` 原則7に従い、**発注先の層を上げるのではなく、発注文書を書き直す。**

- **理解は正しいが計画が甘い** → 同じ層のまま強度を上げる
- **問題の枠組みを取り違えている** → 発注文書の仕様が不足している。仕様を詰めて再発注する

T3・T8・T9 で Terra が2回連続で受入テストを通せなかった場合、Sol へ昇格させず、受入条件の記述を見直す。2回失敗する発注は、モデルではなく仕様に問題があると判断する。

### 10.5 サブエージェントへの委託

上位モデルが担当する作業でも、次は下位へ委託する。

**委託してよい**

| 種類 | 委託先 | 例 |
|---|---|---|
| 資料の収集と該当箇所の抜き出し（判断を伴わない） | Claude Haiku 4.5 / Codex Luna | 古語辞典・単語帳から候補語と出典を並べる |
| 大量項目への同一処理 | Claude Sonnet 5 medium | T4 の600件の差分抽出と分類候補付け |
| 網羅性チェック | Claude Sonnet 5 medium | 規則×難度マトリクスの空きセル列挙、カバレッジ集計 |

**委託してはいけない**

- 不一致が「規則の穴」か「データの誤り」かの裁定（T4 の核心）
- 受入テストの期待値の決定（T2・T7）
- 規則表への追記可否の判断
- `確認状態=照合済み` のフラグ設定（`CONSTITUTION.md` 第3条により人）

T4 が代表例である。600件の差分抽出と一次分類は Sonnet 5 のサブエージェントへ並列に投げられるが、**裁定は Opus 5 xhigh が全件を見る**。機械的な部分を剥がすことで、最も高い強度を要する判断に資源を集中できる。

## 11. 検証と受入条件

### 11.1 テストの選び方

`CONSTITUTION.md` 第9条に従う。

- **コンバータと習熟度計算は自動テスト必須**（正本変換にあたる）
- **語データの追加は CI 検査のみ**（コンバータが通れば可）
- **文言・色・余白の変更に全件検査を回さない**

### 11.2 受入条件

次を代表環境で確認できた版だけを公開する。

1. 規則表の16規則すべてに典拠があり、`出題対象` が明示されている
2. コンバータが添付資料の演習6問と規則別代表例をすべて正しく変換する
3. 百人一首600件の不一致がすべて裁定され、例外が規則表に記録されている
4. 全収録語で、コンバータ出力が `現代仮名遣い` 列と一致するか、例外として明記されている
5. 全収録語が `確認状態=照合済み` で、`典拠` を持つ
6. 出題対象13規則が単独3例以上、複合が2例以上ある
7. 「変化なし」語が規則語全体の15〜20%である
7a. 例外語が `親規則`・`例外の型`・`通常なら` を持ち、規則語と分離されている
7b. 例外語が親規則の規則到達度60未満では出題されず、出題比率が10〜15%を超えない
7c. 規則到達度の計算に例外語が含まれない
7d. `itemKey = wordId` であり、複数規則が絡む語の1回の正答が複数キーへ加点されない（裁定 D-01）
8. NFC 正規化、カタカナ→ひらがな、空白除去が動き、長音符が誤りとして扱われる
9. 誤答診断が、規則の部分適用と過剰適用の両方を特定できる
10. 習熟度の増分・上限、ヒント段階による一段軽い扱い、同一回半分、90超の別日想起を自動テストで検証できる
11. 端末内の逐次保存、書き出し、既存記録を消さない重複排除マージ、初期化確認が動く
12. 書き出しJSONが百人一首アプリと共通スキーマで、`itemKey` のみ異なる
13. 320/375/414/768px、iOS Safari、Android Chrome、iPad Safari、キーボード、読み上げ、200%拡大で重大な操作不能がない
14. IME で変換せずひらがなのまま送信でき、Enter が送信に割り当てられていない
15. 公開物に秘密情報、実利用データ、許可未確認の原資料が含まれない

既知の制約（句・短文の出題、匿名統計、クラウド同期を初回公開に含まないこと）は「完全対応」と表現せず、使い方と変更履歴に明記する。
