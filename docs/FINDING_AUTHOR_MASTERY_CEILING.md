# 所見: 歌の習熟度が100%に到達できない

記録日: 2026-09-09（ポイント機能の実装中に発見）

## 実測

`packages/shared/src/domain/mastery/` を直接動かして計測した。

| 条件 | 結果 |
|---|---|
| 本文 `p001:text` を自由入力で200回正答 | 100 |
| 作者 `p001:author` を選択式で200回正答 | **65** |
| 歌全体 `poemMastery`（本文0.8 + 作者0.2） | **93** |
| 参考: 作者も自由入力で出題された場合 | 作者100 / 歌全体100 |

## 原因

`packages/hyakunin/src/domain/entry.ts:97` が出題候補を次のように絞っている。

```
question.type === 'blank' || (includeAuthors && question.questionId.endsWith('-author-choice'))
```

`quick` / `author` / `exam` はこの絞り込みを通るため、**作者は選択式しか出題されない**。
選択式の上限は `rules.v1.ts` の `choice: { increment: 5, cap: 65 }` なので、作者は65で止まる。

`-author-kana` と `-author-free` の問題データは `tools/build-data/questions.ts:71,75` で
生成済みで実在する（`packages/hyakunin/src/data/generated/questions.author.json`）。
**出題経路が通っていないだけ**である。

`review` 経路は過去に答えた questionId を出し直すだけなので、選択式しか答えていない以上
ここからも上位方式は出ない。

## なぜ問題か

依頼者裁定（2026-09-09）:「作者も歌も、何回も確実に正解したら100%という指標としたい」。
93%が上限では、この指標が成立しない。

## 直すときの注意

- **`MASTERY_RULES_VERSION` を上げないこと。** `computeMastery` は版が違うイベントを
  丸ごと無視するので、上げると全利用者の習熟度が0に戻る。
- `entry.ts:97` のコメントは「初回に出す作者問題は候補の順序まで生成データで確定した
  4〜5択だけである」と書いている。**初回を選択式にすること自体は意図的な裁定**なので、
  初回を壊さず、習熟が進んだ歌だけ上位方式へ上げる形にすること。
- 到達可能性そのものを試験で釘付けにすること。今この上限を守る試験は1本も無く、
  だからこそ静かに93で止まっていた。

## 追記（2026-09-09・依頼者裁定）

100% の条件を、最終的に**全文記述**にしたいという裁定が出ている。

> 問題設定が句ごとしか出ていないので、難度設定を実装することを想定した傾斜としたい。
> 最後は作者まるごと書ける・また、一首まるまる書けないと100にならない、という設定を設けたい。

現状の到達経路を整理すると、必要な作業は次の2つである。

| 100 の条件 | いまの状態 |
|---|---|
| 作者をまるごと書ける | **問題データは実在する**（`-author-free`）。出題経路が無いだけ。上の本文で述べた天井の問題と**同じ1件**である |
| 一首をまるまる書ける | 問題データが無い。句ごとの空所補充（`type: 'blank'`）しか無く、新しい出題形式が要る |

つまり作者側は「経路を通す」だけ、本文側は「新しい出題形式を作る」。作業の重さが違うので、
分けて発注してよい。

### すでに入れてある足場

`packages/shared/src/domain/mastery/rules.v1.ts` の `isMasteryCompletionMethod()` が
「90 を超えて 100 へ進める資格のある方式」を1箇所で判定している。いまは
`isRecallMethod()`（句ごとの自由入力・紙手書き）をそのまま返しているが、
**全文記述の方式が入ったら、この関数の中身だけを差し替えればよい**。
`compute.ts` を含め、呼び出し側は触らずに済む。

差し替えると 90 が当面の天井になる（全文記述の出題がまだ無いため）。
そこで足踏みする学習者にはポイントが伸び続けるので、数字が止まることにはならない。

## 追記（2026-09-09・発注081で実装したときに分かった訂正）

**この所見の「出題経路が通っていないだけ」は不正確だった。** 実装して分かった訂正が2件ある。

1. **出題画面も直す必要があった。** `Session.tsx` は `question.type === 'author'` だけで
   選択式として描画していた。`-author-free` は候補が空なので、出題経路だけ通すと
   **選択肢ゼロの回答不能な画面**が出る。「作者問題か」と「選択肢を並べるか」を分けた。
2. **kana の段は現状では働かない。** `-author-kana` の問題データは実在するが、
   **`kanji-to-kana`（上限80）を記録する経路が出題画面に無い**——`Session.tsx` が出す方式は
   choice / free-input / paper-handwriting の3つだけである。出しても自由入力として記録されるので、
   梯子は選択式→自由入力の**2段**にした。kana を段として使うなら、方式の配線を足すところからになる。

実装と検収の記録は [発注081の引き継ぎ](HANDOFF_AUTHOR_MASTERY_2026-09-09.md) にある。
上の「作者側は経路を通すだけ」という見積りは、**この2件のぶん軽く見ていた。**
