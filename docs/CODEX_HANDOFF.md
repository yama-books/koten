## 2. 検収の体制（**2026-09-05 変更。ここが今回いちばん大事である**）

### 2.1 何が変わったか

**これまでは「親担当（Claude）が全コマンドを再実行して検収する」だった。**
**依頼者の資源都合により、これを一時休止する。**

**過去の発注書・`HANDOFF.md` に「親担当が検収する」と書いてある箇所は、本節で読み替える。**
**同じ規約が複数の文書に散っているため、全部は直していない。本書が新しい。**

### 2.2 検収セッションの立て方（**この 4 条件を満たさない検収は検収と呼ばない**）

| # | 条件 | なぜ |
|---|---|---|
| **V-1** | **実装したセッションを引き継がない、新しいセッションで行う。** 同じ会話に実装や測定の記憶が入っていたら受け直す | **証人の性質は context の独立性から来る。** 自分の測定値を思い出して答えると、一致しても何も証明しない（発注055 §7 の S-0 と同じ） |
| **V-2** | **報告の数値を転記しない。全コマンドを自分で再実行し、出力を貼る** | **実行していない検査を成功と書いた事故が過去に複数ある**（`HANDOFF` 2026-08-31 の Luna 評価） |
| **V-3** | **破壊試験を最低 2 行、自分で当て直す。** 当て直す行は**実装側に事前に知らせない** | 監査する行を知っている者に測らせても、確かめていない行の保証にならない。**知らせたつもりで参照先の文書に残っていた事故が 2026-09-05 に起きた**（§5 の落とし穴 3） |
| **V-4** | **判定は「合格 / 条件付き合格 / 差し戻し」の 3 値で書き、条件付きなら条件を機械判定できる形で書く** | 「おおむね良い」は次の担当が使えない |

### 2.3 検収の手順（**発注056 の場合。以後の発注も同じ形で作る**）

1. **基準線を採る**——§0 の 4 つ。**着手時の値を先に控える。**
2. **受入条件を上から全部実行する**——056 §7.1 の 9 コマンド。**終了コードと件数を貼る。**
3. **釘の本数を数える**——056 は `test:screen` が **15 files / 132**（128 ＋ F-1〜F-4）になるはずである。
   **合わなければ、増えた／減った試験名を挙げる。**
4. **抜き取りの破壊試験**（V-3）——056 §6 の 10 行から **2 行以上**を選び、
   `cp` で控え → 壊す → **`grep -c` で当たったことを確かめる**（検索語と対象ファイルを併記）→ 測る → `cp` で戻す。
   **`git diff` が空であることで復元を確かめる。`git status` で判定しない**（索引の stat が古いと `modified` と出る）。
5. **変更境界を見る**——`git diff --numstat <着手時HEAD> -- packages` が **0 行**であること。
   056 は製品を恒久変更しない発注である。
6. **判定を書く**（V-4）。**記録先は `docs/HANDOFF.md` §8 の先頭**（新しい節を足し、前の節に「古い」と書く）。

## 5. 落とし穴（**実測で踏んだものだけ。短く読める形にした**）

1. **基準線を commit ハッシュで書かない。** **`git diff --stat <実装が最後に動いた commit> HEAD -- packages tests` を実際に走らせて、出力を貼る。**
   **`docs/` の commit は基準線を動かさない。** 親担当はこの誤りを 3 回続けた（053・054・055）。
2. **復元は `cp` で行う。** **Python で書き戻すと改行が化けてハッシュがずれる。**
   **復元の確認は `git diff`。** **`git status` は索引の stat が古いと `modified` と言う。**
3. **同じ制約が 2 箇所にあると、片方しか直らない。**
   2026-09-05、発注055 は「監査する 2 行を伏せる」と直したのに、**Terra が壊し方を読みに行く 054 の末尾に 2 行の名前が残っていた。**
   **伏せると決めたら、相手が読む文書を全部 `grep` してから「伏せた」と言うこと。**
4. **`grep -c` は検索語と対象ファイルを併記する。** 件数だけ書くと、後から数え直しても合わせられない（発注055 で実際に合わなかった）。
5. **「壊したのに全部緑」の原因の 1 位は、破壊が当たっていないこと。** **先に `grep -c` が 0 でないことを見る。**
6. **破壊が「赤くならず、終わらない」ことがある**（棄却サンプリング・繰り返し）。**1 回の実行に 5 分の上限を必ず付ける。**
7. **1 行の破壊で全部赤くなったら、別の欠陥を叩いている。** **感度（壊れたら赤い）と特異度（1 本だけ赤い）は対で測る。**
8. **「無いこと」を見る釘は、走査対象が空でないことを先に assert する。** 空のまま数えると、実装が 0 件でも緑になる。
9. **免除したファイルは、別の検査が拾わない限り全部書き放題になる。** 名指しで検査の外に出すときは、代わりの網を書く。
10. **実行していない検査を成功と書かない。** **検査ツールは完走しなかったときに合格を出してはならない。**
    （過去に、サーバ起動に失敗して 1 件も測っていない状態で「1200 件合格」と出したツールがある。）
