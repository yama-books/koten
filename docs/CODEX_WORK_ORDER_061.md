## 3. 裁定（**2026-09-06 確定**）

依頼者の意向は「配線できるならば配線したい」である。一方で**送信は取り消せない唯一の操作**である。
そこで**配線は行い、不可逆な部分だけを封じ込める**形で裁定する。

### 裁定1：配線する。送り先は test に固定する

**案Bを採る。** 配線し、同意の通知を戻し、`stats_days_test` へ送る。

**ただし `stats_days_official` へは送らない。** テスト公開版を名乗っている間に `official` へ入ると、
**後から分離できない。** 正式公開を名乗る時点で改めて裁定する（裁定4）。

**送信は最後に配線する。** §4 の順序を守り、(1)〜(3) が緑になるまで `fetch` を書かない。

### 裁定2：通知のみ。オプトアウトは出さない【**2026-09-06 確定（同日に1度改め、元へ戻した）**】

**依頼者裁定（2026-09-06）。** 一度「止める手段を置く」で確定したが、**同日中に元へ戻した。**

- **初回利用時に送信の可否を選ばせない。** 059 R2 の形（タイトルより下のコンパクトなダイアログ、
  学年は必須、OKで消え、確認済みなら再表示しない）で**通知のみ**を示す。ボタンは「確認する」のまま。
- **オプトアウトは画面に出さない。** 依頼者の理由——**送る中身に個人を特定する情報が無く**、指導上、

- **仕組みは残す。** `UserSettings.statsOptOut` と `canSendStats()` は止める判定を持ち、単体試験もある。

### 3b. 【解決済み】裁定2 と `APP_SPEC` §11 の衝突

`APP_SPEC` §11 は次を明記している。

> 統計送信について、初回利用時に次の簡潔な説明を示す。**初回公開では個別のオプトアウト機能を設けない。**

**上の裁定2（「送らない」を対等に置く・あとから取り消せる）は、この行と正面から矛盾する。**
既存の画面が「同意する／しない」ではなく「**確認する**」だったのは、§11 のこの設計に沿っていたからである。

**どちらも成り立つ設計であり、実装者が選んでよい種類の差ではない。**

- §11 のまま（通知のみ・オプトアウトなし）：送る中身が §11 の制限（無作為番号・自由記述なし・問題別履歴なし・
  時刻とIPを保存しない）を満たす限り、集計としては筋が通る。実装も小さい。
- 裁定2 のまま（断れる）：**利用者に中学生を含む。** 断る力が対等でない相手に対しては、
  通知だけでなく選択肢を置く方が安全側である。ただし §11 の改訂になる。

**2026-09-06、依頼者が裁定した**——「初回は通知のみ。あとから止められる」。`APP_SPEC` §11 を改訂済み。
**§4 の (3) へ進んでよい。**

なお依頼者へ説明した実害の見立てを記録しておく。**送る中身に個人へ戻る手がかりが無く、受け取る側に名簿も無いため、
番号から個人を割り出すことは実際上できない。** ただし**通信する以上、IPアドレスは通信相手のログに届きうる**——
アプリからは送らないが「どこにも一切残らない」とは言えない。**この点を「個人が特定されない」の根拠に含めないこと。**

### 裁定3：送る中身

`StatsPayload` は次を持つ——`clientNumber`・`localDate`・`product`・`grade`・`pageViews`・`buttonCounts`・`entryCounts`・`questionTypeCounts`・`attemptCount`・`masteryAvg`・`masteryMax`・`masteryDistribution`・`isOfficial`・各版番号・`expiresAt`。

**現行の `StatsPayload` のまま送ってよい。** ただし次を守ること。

- **学年は4区分（中一・中二・中三・その他）と「答えない」だけ。** 自由入力や学校名を足さない。
- **`clientNumber` は端末ごとの乱数であり、こちらから個人へ戻せないこと**を実装で確かめる。
- **自由記述を混ぜない。** 問題報告の利用者コメントは端末内に留め、統計へ相乗りさせない。
- 上を満たす限り、画面の「個人が特定されることはありません」は言い切ってよい。
  **項目を1つでも足すときは、この裁定を取り直すこと。**

### 裁定4：`isOfficial` は false 固定。切り替えは別の裁定

**本発注では `isOfficial: false` を定数として固定する。** 設定や環境変数で切り替えられるようにしない——
**切り替えられる作りにした時点で、事故で `official` へ入る道ができる。**

正式公開を名乗る段になったら、そのときに `true` にする変更を1件の発注として起こす。
その発注の受入条件には「`test` 側の既存データと混ざらないこと」を必ず含めること。

| 決めたこと | 実装 |
|---|---|
| 保持期間 **1年** | `STATS_RETENTION_DAYS = 365`・`expiresAtFrom()`。**ここが唯一の出どころ** |
| 送るのは**終わった日だけ** | `finishedDay()`。今日は返さない——途中の数を送ると1日が二重か欠けで確定する |
| 失敗は再送へ | `retry` なら送信待ちへ。次の起動で再試行。保持期間を過ぎた分は捨てる |
| 例外を投げない | 圏外・応答の破損・認証失敗、すべて `retry`。**画面には何も出さない**（§11） |
| 重複しない | 同じ日を二度送ると Firestore の 409 を `sent` として扱う |

**カウンタの順序に要注意。** 起動時は「**先に古い日を読んで送り、そのあと今日の分を数え始める**」。
逆にすると、まだ送っていない前日の数を今日として数え直してしまう。
