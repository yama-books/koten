### 「一首まるまる」だけは別物である（重要）

出題画面は `blankPattern = /＿+/` で prompt を分割し、**空欄1つ**を描画する
（`Session.tsx` の `PromptLine`）。答えも `question.answer` 1つである。
**一首まるまるは空欄が5つあり、答えも5つ**なので、
「1問＝1空欄1答え」という前提そのものを変える必要がある。

依頼者は「一首まるまる」を優先指定しているが、**3つの中でこれが一番重い。**
粒度と漸増は同じ選択ロジックの上に乗るが、一首まるまるは出題・採点・記録の形が変わる。

**この見積りは私の判断であり、実装して確かめてはいない。**
発注081で「経路を通すだけ」が2件ぶん外れた前例があるので、
**着手する人は `Session.tsx` の採点経路（`submit` と `buildEvent`）を先に読むこと。**

### 正誤判定の正本は「読み」2ファイルであり、`sourceRef` の一次データではない

`tools/build-data/paths.ts:10-13` が読むのは4ファイルで、役割が分かれている。

| 役割 | ファイル |
|---|---|
| 本文・作者 | `百人一首_本文・作者_一次データ.md` |
| **歴史的仮名遣いの読み**（○の正解） | **`百人一首_読み_歴史的仮名遣い.md`** |

| 読み方式の異同 | `百人一首_読み_異同確認.md` |

**問題データに焼き込まれる `sourceRef` は `百人一首_本文・作者_一次データ.md` である**
（`tools/build-data/index.ts:21`）。**出典表示と、仮名の正誤を決めているファイルは別物**である。
「`sourceRef` を見れば正本が分かる」と読むと、照合する相手を間違える。

### `confirmed` は PDF 照合が済んだ意味ではない

`reading.status: 'confirmed'` の意味は「**異同確認の資料に未決着の読み方式が無い**」であって、
「人が台帳で承認した」ではない。**この2つが同じ語で呼ばれていたことが G-3 の正体だった**
（[HANDOFF.md](HANDOFF.md) §4.1）。いま100首すべて `confirmed` だが、
`review/readings.yaml` は100首とも `pending` のままである。**照合はこれからである。**

関連して依頼者の見立てが記録されている——71番の「葦」は原本PDFに対しWEBから漢字が
補われたもので、**他にも同型が残っている見込み。全首の原本照合は今後の要検証事項**。

### 発注082は読みの値に触れていない

作者の自由記述を ○ にした発注082が動かしたのは `poem.reading.modern.author` の
**置き場所（`partialAnswers` → `acceptedAnswers`）だけ**である。**読みの値そのものは1文字も変えていない。**
PDF との異同が存在するなら、082 の前後で変わっておらず、上の2ファイルの内容の問題として残っている。

### 照合後に直すときの安全網と禁止事項

- 読みを直したら `npm run data:build` で問題データが再生成され、`acceptedAnswers` が変わる。
  このとき **`tests/data/mixed-kana-orthography.test.ts` が効く**——歴史的と現代を取り混ぜた綴りを
  組み立てて `judge` へ通すので、**片方だけ直して混在状態になったデータがあれば赤くなる。**
- **`MASTERY_RULES_VERSION` は上げないこと。** 読みの修正で上げると**全利用者の習熟度が0に戻る。**
- `manifest.json` の `generatedOn` も一緒に動く。生成物なので同じコミットに入れる（発注082で入れ損ねた）。
