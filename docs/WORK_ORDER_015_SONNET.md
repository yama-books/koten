# 発注文書 015: 偽合格の全数監査 —— 検査ツールと試験の因果を確かめる

発注日: 2026-08-31
担当: **Sonnet**（Codex ではない。`CODEX_WORK_ORDER_*` と番号帯を共有するが、担当が異なるため別名にした）
階層: 該当なし（**読み取り専用の監査**。製品コードを一切変更しない）
着手時期: **即時。発注013・014 と並行してよい**（本発注はコードを変更しない）
優先度: 高（同種の偽合格が他の検査に潜んでいる可能性が高い。公開ゲートの信頼性に直結する）

## 0. 背景 —— 検査が緑でも実装が壊れていることがある

2026-08-31、親担当が発注009 を検収し、**不合格**とした。
検査は全部緑だったが、破壊試験で次が判明した。

| # | 場所 | 実測した事実 |
|---|---|---|
| F-1 | `tools/check-storage/index.ts` | `packages/shared` から何も import せず、スキーマをブラウザ内で再実装していた。**保存層を丸ごと退避しても 4/4 合格した** |
| F-2 | 同 58〜64 行 | 「容量不足」シナリオが、自分で投げた例外を自分で捕まえて判定していた。`writeFallback` は呼ばれていない |
| F-3 | `tests/unit/storage/storage.test.ts` | 「upgrade 例外で abort し既存データを保持」の試験で、**`db.ts` の `abort()` を削除しても 6/6 合格した** |

**3 件とも、報告は正直だった。検査が嘘をついていた。**
だから報告を読んでも見つからない。壊してみるしか見つける方法が無い。

**この 3 件が偶然だとは考えていない。** 同じ手癖が他の検査にも入っている前提で探す。
それが本発注である。

## 1. この発注の主題

**`tools/**` と `tests/**` のすべての検査項目について、
「この検査を赤くするには、どの製品コードをどう壊せばよいか」を 1 行で書けるかを確かめること。**

書ければその検査は生きている。書けなければ所見である。

**直さないこと。** 本発注は監査であって修理ではない。
見つけたものは報告し、修理は別発注で出す。

## 2. 変更境界

### 作ってよいファイル

```text
docs/AUDIT_2026-08-31_false-pass.md      （新規。これ 1 つだけ）
```

### 変更してはならないもの —— **リポジトリの他のすべて**

```text
tools/**            tests/**            packages/**
package.json        docs/ の他のすべて   CONSTITUTION.md
一次データの .md ファイル群              .github/
```

`git commit` / `git push` をしない。既存の未コミット変更に触れない。
**新しい npm 依存を追加しない。**

> **発注013・014 が同じ木の上で動いている。**
> `package.json` の `test` script、`tests/unit/storage/storage.test.ts`、
> `tools/check-storage/**`、`tools/overflow-check/index.ts` は**変更中**である。
> これらを監査対象から外す必要はないが、**「現在こう書かれている」という所見は
> 変更中である旨を添えて書くこと。** 修理の重複提案をしないこと。

## 3. 探すもの —— 実証済みの 3 類型

### 類型1: 自己完結（F-1 型）

検査ツールが、検査対象の実装を import せず、内部に写しを持っている。

> **見つけ方:** 各検査ツールの import 文を全部読む。`packages/` を出所とするものが 1 つも無ければ、
> そのツールは何を検査しているのか説明できないはずである。
> 定数・スキーマ・許可リスト・閾値がツール内に直書きされていないか。

### 類型2: 同語反復（F-2 型）

自分で作った値を自分で検査している。実装を通っていない。

> **見つけ方:** その assert が参照している値が、**どこで作られたか**を辿る。
> 試験の中で作られ、製品コードを一度も通らずに assert に届いているなら同語反復である。

### 類型3: 不動の期待値（F-3 型）

どの経路からも変更され得ない値について、変わっていないことを主張している。

> **見つけ方:** assert の左辺が変わりうるかを問う。
> 「この行に到達する時点で、この値が別のものになっている実行経路は存在するか」に
> 答えられなければ所見である。代役（fake / stub）の空実装が典型である。

### 類型4 以降

**3 類型に当てはまらない偽合格を見つけたら、新しい類型として名前を付けて書くこと。**
たとえば次のようなものを想定しているが、これに縛られなくてよい。

- 検査対象が 0 件でも「全件合格」と出る（空集合の合格）。
- 例外を握り潰して合格側に倒れる。
- 終了コードを立て忘れており、不合格を出力しても `npm run` が成功する。
- 検査ツール自身が落ちたとき、合否を出してしまう。

---

## 4. 方法

### 4.1 全数を数える

最初に、監査対象のファイルを**列挙して数える**。

- `tools/` 配下の全ツール（現時点で `build-data` / `scan-publish` / `overflow-check` /
  `font-check` / `font-assets-check` / `font-weight-check` / `check-storage`。
  **列挙は自分で取り直すこと。この一覧を信用しない**）
- `tests/` 配下の全 `*.test.ts`

**使ったコマンドと件数を報告に書くこと。** 監査表の行数がこの件数と合わない場合、
合わない理由を書くこと。**「主要なもの」で済ませないこと。**

### 4.2 検査項目ごとに 1 行

各検査項目について、次の表を埋める。

| 列 | 内容 |
|---|---|
| 場所 | ファイル名と行 |
| 何を検査していると称しているか | 試験名・出力の文言から |
| **赤くする壊し方** | どの製品コードをどう壊せば落ちるか。**1 行で** |
| 判定 | 生 / 所見（類型番号） |
| 確度 | 実験で確認した / 読解のみ |

**「赤くする壊し方」が書けないものが所見である。** それが本発注の唯一の判定基準である。

### 4.3 実験してよい。ただし手順を守ること

読解だけで確信が持てないときは、実際に壊して確かめてよい。**推奨する。**
ただし次を厳守すること。

1. 壊す前に対象ファイル（またはディレクトリの全ファイル）の SHA-256 を記録する。
2. 壊す。検査を実行する。出力を保存する。
3. **直ちに元へ戻す。**
4. SHA-256 を再計算し、1 と一致することを確認する。**一致を報告に書く。**
5. 元の検査を実行し、合格に戻ることを確認する。
6. **次の実験へ進む。**

**1 件ずつ行うこと。並行して壊さないこと。**
**復元できなかった場合は、その時点で全作業を停止し報告すること（§6 の S-A）。**

`git status --short` は未追跡ファイルを `??` としか出さないため、**復元の確認にならない。**
SHA-256 で確かめること。

### 4.4 較正 —— 既に判明している 3 件

F-1・F-2・F-3 は**答えが分かっている**。監査表に含めること。
含めた結果が §0 の実測と食い違うなら、**監査の方法が間違っている。**
先に進まず、食い違いを報告すること。

参考までに、親担当が実際に使った壊し方を書いておく。

- F-1: `packages/shared/src/storage/` を丸ごと退避 → `check:storage` が 4/4 合格のまま
- F-3: `packages/shared/src/storage/db.ts` の `request.transaction?.abort();` を削除 → 6/6 合格のまま

## 5. 受入条件

1. `docs/AUDIT_2026-08-31_false-pass.md` が存在し、次を含む。
   - §4.1 の列挙コマンドと件数。
   - **全数の監査表**（§4.2 の 5 列）。取りこぼしがないこと。
   - 所見の一覧。各所見に**再現手順（コマンド）**が付いていること。
   - 所見ごとの深刻度と、**なぜその深刻度なのか**（何を見逃すか）。
   - **直し方の提案。ただし直さないこと。**
2. F-1・F-2・F-3 が監査表に含まれ、所見と判定されている。
3. `git status --short` の差分が、**`docs/AUDIT_2026-08-31_false-pass.md` の追加 1 件のみ**であること。
   **これを報告に貼ること。** 他に差分があれば、実験の復元に失敗している。
4. 実験を行った場合、§4.3 の 1〜6 を全件について報告している。

### 5.1 親担当が検収時に行うこと

- 監査表からいくつかを無作為に選び、書かれた「壊し方」を実際に実行する。
  **書かれたとおりに赤くならなければ、その行は誤りである。**
- 監査表に載っていない検査項目を探す。**取りこぼしは不合格とする。**
- リポジトリの全ファイルの SHA-256 を監査前後で比較する。

## 6. 停止して報告する条件

| # | 条件 |
|---|---|
| S-A | 実験の復元に失敗した、または SHA-256 が一致しない。**直ちに全作業を停止し、失った内容を報告する** |
| S-B | §4.4 の較正で、F-1・F-2・F-3 の再現が §0 の実測と食い違った |
| S-C | 監査の途中で、**記録の消失につながる所見**を見つけた（実装計画の停止条件 S-7 相当）。表の完成を待たず先に報告する |
| S-D | 発注013・014 の変更中のファイルと衝突しそうになった |
| S-E | 新規 npm 依存が必要だと判断した。**依存追加は禁止である** |
| S-F | 監査対象の実行に、ネットワークまたは外部サービスが必要だと判明した |

**どの停止条件でも、`docs/AUDIT_2026-08-31_false-pass.md` 以外を編集してはならない。**

---

## 7. 完了報告に含めること

1. §4.1 の列挙コマンド、件数、監査表の行数。**一致しない場合はその理由。**
2. 所見の件数と、類型ごとの内訳。新しい類型を立てた場合はその定義。
3. **最も深刻な所見 3 件**を、報告の本文にも書く（監査文書を開かずに分かるように）。
4. 実験を行った件数と、**全件の SHA-256 一致の確認**。
5. §5.3 の `git status --short` の出力。
6. §6 の停止条件に当たった項目。なければ「なし」と明記。
7. **独自に決めたことがあれば全件。なければ「なし」と明記。**
   検査項目の数え方、類型の割り当て基準、深刻度の付け方など、
   本書に書かれていない判断は小さくても全部書くこと。

推測・予定ではなく観測結果を書くこと。
**確かめていない「壊し方」を、確かめたかのように書かないこと。**
読解だけで書いた行は、確度の列に「読解のみ」と正直に書くこと。**それは減点ではない。**
