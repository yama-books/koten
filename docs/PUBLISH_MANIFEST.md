## 1. このファイルの位置づけ

**公開リポジトリへ移してよいものは、この文書に列挙されたものだけである。**

- これは**許可リスト**である。除外リストではない。
- **ここに載っていないものは、載っていないという理由だけで移さない。**
  「移してよいか迷った」は「移さない」と同義に扱う。判断は追記の手続き（§7）を経る。
- 列挙漏れが起きた場合、失われるのは「公開物が 1 つ足りない」ことである。
  除外リスト方式では、列挙漏れは「公開してはいけないものが公開される」になる。
  **この非対称性が許可リストを選んだ理由である。**

`.gitignore` との役割の違い:

| 文書 | 決めること | 効き先 |
|---|---|---|
| `.gitignore` | この（非公開）リポジトリで追跡しないもの | 現リポジトリ |
| **この文書** | 公開リポジトリへ移すもの | P12 の移管作業 |

現リポジトリは非公開であり、原資料 PDF と内部資料を含んだまま存続する（裁定 H-01）。
公開側への流出は `.gitignore` ではなく**この許可リストだけ**が防ぐ。

### 5.1 公開staging（ビルド成果物）の機械可読な許可リスト

§5 のブロックは**リポジトリ内のソース**に対する許可リストである。`tools/scan-publish` が
`packages/*/dist/**` を走査するときは、ソースのパス形ではなくビルド後の成果物を見るため、
別の根拠が要る。**2026-08-31、親担当が次を裁定した。**

`tools/scan-publish` はビルド成果物の各ファイルの拡張子を、次のブロックだけを根拠に照合する。
ここに無い拡張子は一致しないものとして違反にする。ツール側に許可を書き込まない。

```text
# build-artifact extensions
.html
.js
.css
.json
.woff2
.txt
.svg
.png
.ico
```

裁定の根拠と意図:

| 拡張子 | 根拠 |
|---|---|
| `.html` / `.js` / `.css` | §4.1・§4.2 の公開単位が Vite の静的ビルドである以上、必ず出る |
| `.json` | `packages/*/src/data/generated/**` がアセットとして出る（`dist/assets/poems-*.json` を実測） |
| `.woff2` | §3.6。H-02 完了により self-host が可能。実ファイル作成は P3 残件 |
| `.txt` | §3.6 の「各フォントのライセンス原文ファイル」（`OFL.txt`）の同梱義務に対応 |
| `.svg` / `.png` / `.ico` | `packages/*/public/**` と `assets/feedback/**`。現時点で実体は `404.html` のみ |

**意図してここに載せなかったもの（載せれば違反として検出される）:**

- `.map` — ソースマップは公開しない。内部のファイル構成と未公開コードが露出するため。
- `.md` — ビルド成果物に一次データやドキュメントが混入した状態を検出するため。
- 拡張子なしのファイル — 想定外の混入を必ず気づけるようにするため。

この表と上のブロックが食い違った場合は**表が正**であり、ブロックを表へ合わせる。

### 6.1 `古典文法_一次データ索引.md` を初回公開に含めない判断（**新規・人間確認 H-14**）

計画 §14.2 は「一次データ Markdown 5 点」を移す対象として挙げており、本ファイルはその 1 点に当たる。
しかし P0 で内容を確認した結果、**初回公開の許可リストには含めない**ことにした。理由は 3 つある。

1. **初回公開に不要である。** 本ファイルは助動詞機能のための索引であり、その機能フラグは v1 で `false`（計画 §4.3）。
   仮名遣いツールも百人一首アプリも、初回公開でこのファイルを参照しない。
   **公開して得るものがない一方で、下の 2 点の risk を負う。**
2. **原表の構成をなぞった転記を含む。** 「主な意味（原表の分類）」「主な接続」「活用型」を助動詞ごとに表にしている。
   2026-08-30 の裁定は「文法事実（意味・接続・活用型）は参照可。**原表の表現・語順の転記は避ける**」であり、
   本ファイルの表はこの線の内側にあるとは言い切れない。判断は人が行うべきものである。
3. **ローカル絶対パスを含む。** `H:/USB-3211.pdf` 等。正本は読み取り専用のため P0 では修正しない。
   公開するなら、公開用に書き直したもの（`要書換`）として扱う必要がある。

**H-14 として人間の判断を仰ぐ。** 判断が要るのは次の 2 点である。

- 助動詞機能を実装する段（v1 より後）で公開する前提でよいか。
- そのとき、原表の語順に依らない形へ書き直した版を公開するのか、公開しないのか。

判断が出るまでは**移さない**。§1 の原則（迷ったら移さない）に従う。

## 7. 追記の手続き

公開物を増やすときは、次をすべて満たしてから表に行を足す。

1. **そのファイルが初回公開に必要である**ことを述べる。「あっても害がない」は理由にならない。
2. 第三者の権利が絡む場合、`docs/LICENSE_AUDIT.md` に確認結果があること。未確認なら `条件つき` にする。
3. 個人情報・秘密情報・ローカル絶対パスを含まないことを確認したこと。
4. §5 の機械可読ブロックにも同じパスを足したこと。
5. `docs/HANDOFF.md` の「決定の記録」に、追記した理由を残したこと。

**削るときは 4 と 5 だけでよい。**（減らす向きの変更は公開事故を起こさない）

## 8. P12 での使い方

1. 新しい GitHub アカウントに**空のリポジトリを作り、`git init` から始める**（裁定 D-03）。
   現リポジトリに remote を足さない。`git push` で移さない。
2. §5 の機械可読ブロックに列挙されたパスだけを、新しい作業ツリーへ**コピー**する。
3. `要書換` の項目は、コピーではなく公開用に作り直したものを置く。
4. `条件つき` の項目は、`docs/LICENSE_AUDIT.md` の確認状態が「確認済み」であることを見てから置く。
5. `tools/scan-publish` を実行し、検出件数 0 を確認する。
6. 新しい作業ツリーの全ファイル一覧を出し、§5 のブロックと**1 対 1 で突き合わせる**。
   ブロックにないファイルが 1 つでもあれば、その場で止めて原因を調べる。
7. `git config user.name` / `user.email` を公開名義に設定してから最初のコミットを作る（§14.4・H-09）。
   **`user.email` は `<ID>+<アカウント名>@users.noreply.github.com` とする（裁定 D-10、ADR-0003 追補）。実メールアドレスを設定しない。**
   アカウント側で `Keep my email addresses private` と `Block command line pushes that expose my email` を有効にしておくこと。
