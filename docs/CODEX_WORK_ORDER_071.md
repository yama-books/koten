## 0. 何を確定したか（**調べ直さなくてよい。実測済みである**）

**`reading.status: 'confirmed'` の意味は「異同確認の資料に未決着の読み方式が無い」である。**
**「人が `review/readings.yaml` で承認した」という意味ではない。**

| 事実 | 根拠 |
|---|---|
| `status` は `readingReviewCardNumbers(variants)` に入る首だけ `review`、他は `confirmed` | `tools/build-data/index.ts` の `poems` 生成 |
| その集合は**いま空（0首）** | 読み方式の異同は2件。どちらも `UNSETTLED`（保留・未確定・未決・要確認…）に当たらない |
| 読み台帳の分岐は**どの首も変えられない**（承認済み行に `confirmed` を代入するだけ） | `tools/build-data/apply-review.ts` |
| `kugire` 台帳には**適用経路が1つも無い** | 参照は `validate.ts` の V-09 と件数のみ |
| `layout` 台帳**だけ**が効いている | `apply-review.ts` → `layoutHints` → `emit.ts` |

**この発注は、上を実装で確かめ直す発注ではない。書き留めて、将来ずれないようにする発注である。**

## 1. 工程1：意味を書き留める

- **`review/readings.yaml` の先頭の注記を書き換える。** いまは「読みの確認台帳（人が書き込む唯一の場所）」とだけある。
  **`poems.json` の `reading.status` はこの台帳から来ていないこと**を1〜2行で明記する。
  **`status` の語（`pending | approved | rejected | hold`）そのものは変えない。**
- **`review/kugire.yaml` の先頭に「未使用」と明記する。** 生成物へ適用される経路が無いことを書く。
- **`tools/build-data/index.ts` の `status` を決めている箇所に、意味を1行のコメントで置く。**
  **「異同が未決着でない」であって「人が承認した」ではない**と書く。

**`status` の値そのもの、`review/*.yaml` の各行、生成JSONは1つも変えないこと。**

## 2. 工程2：混ざらないように釘を打つ（**この発注の本体である**）

**次の3本を置く。置き場は `tests/unit/`（`data:check` と同じ層）とする。**

1. **読み台帳は `reading.status` を動かせない。**
   一時ディレクトリで `review/readings.yaml` の**全100行**を `approved` にして生成し直し、
   **`poems.json` が1バイトも変わらない**ことを見る。
   **1首だけで試さないこと**——第1首はもともと `confirmed` で、変化が無くても何も証明しない
   （発注070 の実験がこれで根拠を失った）。
2. **`kugire` 台帳は生成物へ届かない。**
   同じく全100行を `approved` にして生成し直し、**`poems.json`・`questions.*.json`・`layout-hints.json` が
   変わらない**ことを見る。**`manifest.json` は件数を持つので変わってよい。**
3. **`layout` 台帳は生成物へ届く。**
   1行を `approved` にすると **`layout-hints.json` が変わる**ことを見る。
   **これが陽性の対照である。** 1・2だけだと、生成器が壊れて何も出力しなくても全部緑になる。

**`review/` の実ファイルを書き換えないこと。** `tools/review-approve/index.ts` の
`validateBeforeWrite` が一時ディレクトリを使う先例である。

## 3. 変更の境界

**許可**：`review/readings.yaml`・`review/kugire.yaml` の**先頭の注記のみ**、
`tools/build-data/index.ts` の**コメントのみ**、`tests/unit/**` の新規試験、`docs/HANDOFF.md`。
**対象外**：`review/*.yaml` の `entries`（**1行も変えない**）、生成JSON、`packages/**`、
`tools/build-data/` の**動作**（コメント以外）、`firebase/**`、統計、画面。
**弱めないこと**：`data:check`・`npm test`・`scan:publish`・`check:eol` の現状。

## 4. 受入条件

- 工程2の3本が置かれ、**実際に完走した出力を報告に貼ること。**
- **`git diff -- review/` が、先頭の注記の行だけであること。** `entries` に差分が無いこと。
- **生成JSONに差分が無いこと**（`git diff --numstat -- packages/*/src/data/generated` が0行）。
- `npm test`・`data:check`・`check:eol` がすべて緑。
- **`review/` の走査対象が空でないことを、試験の中で先に確かめること**
  （`entries.length === 100` を assert する）。**空の台帳を承認しても何も変わらないのは当たり前である。**

## 5. 破壊試験（3件）

1. `apply-review.ts` の読み台帳の分岐を「`approved` なら `status` を `review` にする」へ変える
   → **釘1だけ**が赤くなること。**これが赤くならなければ、釘1は何も測っていない。**
2. `apply-review.ts` の `layoutHints` の `status === 'approved'` の絞り込みを外す
   → **釘3だけ**が赤くなること。
3. `kugire` を `layoutHints` と同じように生成物へ流す1行を足す
   → **釘2だけ**が赤くなること。

**各回で何件赤くなり、何件緑のまま残るかを報告に書くこと。**

## 7. 検収で繰り返し出ている型（**着手前に読むこと**）

- **fixture は2つの実装を区別できる値にすること。** 発注070 は第1首（もともと `confirmed`）で実験し、
  **「効かない」と「効くが既に `confirmed`」を区別できていなかった。**

- **報告した以外の検査も回すこと。** 発注066 は `scan:publish` を回さず公開ゲートが赤のまま届いた。
