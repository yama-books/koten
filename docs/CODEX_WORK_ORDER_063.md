## 1. 工程1：本番で作者問題の有無を選べるようにする（**着手可**）

### 1.1 裁定：入口は1×3のまま。**範囲選択画面へ設定を置く**

「学習方法を選ぶ」は **歌本文／作者／本番** の3択のまま変えない。
**2×2にしない。新しいダイアログも作らない。** 本番を選んだあとに必ず通る**範囲選択画面**へ、
「作者問題も出す」を範囲・解答方法と並べて置く。

**理由（認知面）**

1. **2×2は次元が混ざる。** 「歌本文」「作者」は*何を*学ぶかの選択、「本番」は*どう*解くかの選択である。
   そこへ「本番（作者あり）」「本番（作者なし）」を並べると、**1つの平面に2つの軸が同居する。**
   学習者は各タイルがどちらの軸に属するかを推論してから選ぶことになり、選択肢の数以上に負荷が上がる。
   **並列に置いたものは同じ種類だと読まれる**という期待に反する。
2. **見分けが括弧の4文字に集約される。** 隣り合う2つが括弧内だけ違う状態は、
   **似すぎた選択肢の対比読み**を強いる。選択肢が1つ増えること以上に効く。
3. **決定の順序が実際の構造と合う。** 活動の種類 → その設定、という段階的な開示になり、
   関係のない段階で問われない。
4. **設定画面はすでに経路上にある。** 新しいダイアログは「もう一つの割り込み」だが、
   範囲選択は**既に想定されている停止点**である。範囲・解答方法と同じ場所へ設定が集まる。

**実務上の理由**：この製品は320px・文字200%で検査している。**2×2は最も狭い条件で確実に崩れる**
（現在の1×3ですら縦積みに落ちる幅である）。4枚目のタイルは、その条件を悪化させるだけの見返りがない。

### 1.2 仕様

- 範囲選択画面（`RangePicker`）に「**作者問題も出す**」を置く。**本番のときだけ**出す。
  歌本文・作者・とりあえずには出さない——それぞれ種別が決まっているためである。
- **既定は「出す」。**「本番のように」は網羅的である方が趣旨に合う。
- **記憶しない。** 毎回の選択とする。記憶させると保存スキーマが増え、書き出し・取り込み・統計の
  それぞれに波及する。**必要になったら別途裁定する。**
- 外したときの出題は**穴埋めのみ**。問題数は変えない（`ENTRY_RULES.exam.questionCount`）。

### 1.3 受入条件（工程1）

- 本番の範囲選択に「作者問題も出す」が出る。**歌本文・作者・とりあえずには出ない**（**4つとも確かめる**。1つ代表では足りない）。
- 既定で選んだとき、出題に**穴埋めと作者の両方**が含まれる。
- 外して始めたとき、出題が**穴埋めだけ**になる。**問題数が変わらない**こと。
- **統計に新しい項目を足さないこと。** 作者を含めたかどうかは `questionTypeCounts` に既に現れる。
- 320px・文字200%で範囲選択画面に違反0。**既存の走査群に本番の範囲選択が含まれているか確かめ、
  無ければ足す**（件数の門を付ける）。
- **破壊試験2件**：(a) 設定を無視して常に作者を混ぜる → 「外すと穴埋めだけ」が赤くなること。
  (b) 歌本文にも設定を出す → 「本番以外には出ない」が赤くなること。
  **各回で何件赤くなり何件緑のまま残るかを記録すること。**

## 2x.（旧）工程2：統計の入口一覧を実装へ揃える

### 2.1 事実

**発注062が入口 `author` を新設したが、統計側は5つのままである。**

- `packages/shared/src/telemetry/registry.ts` の `ENTRY_KEYS` は `['quick','view','learn','review','exam']`。**`author` が無い。**
- `firebase/firestore.rules` も同じ5つを `hasAll` で要求し、**`size() == 5` で固定している。**
- `packages/hyakunin/src/domain/stats.ts` は `session.entry in entryCounts` で弾くため、
  **作者入口の利用は統計に1件も現れない。**

**「指導のために正確な集計を得たい」という目的に直接反する。** 作者は独立した学習入口であり、
使われた回数が見えないのでは入口ごとの利用を比べられない。

**これは発注062の落ち度ではない。** 062の準備書が「統計は対象外」と境界を引いたためで、
**境界の引き方を誤ったのは起草者（Sol役）である。**

### 2.2 順序（**逆にしないこと**）

1. **先に Firestore の規則を6キーへ広げて配置する**（`hasAll` に `author` を追加、`size() == 6`）。
   コンソール作業。`docs/FIREBASE_CONSOLE_TODO.md` §5b。
2. **配置を確認してから**、`ENTRY_KEYS` と `domain/stats.ts` の `entryCounts` に `author` を足す。

**逆順にすると、配置済みの規則が6キー目を拒否し、統計の書き込みが全部失敗する。**
失敗しても学習は止まらず送信待ちへ積まれるが、**その間の統計は1件も残らない。**

### 2.3 受入条件（工程2）

- `ENTRY_KEYS` が6つになり、`isStatsPayload` が6キーの `entryCounts` を通す。
- **5キーの古い形を拒否すること**（両方向で確かめる。緩めるだけの変更になっていないか）。
- `summarizeDailyStats` が作者入口の回を数える。
- `firebase/firestore.rules` の更新分がリポジトリにも入っていること。**配置とリポジトリを食い違わせない。**
- `tests/rules/` の規則試験があれば更新する。
- **破壊試験1件**：`author` を数えない実装へ戻すと、作者入口を数える試験だけが赤くなること。

## 4. 検収で分かったこと（**本発注の実装者も読むこと**）

発注062の検収で、`check:overflow` が**3つの別々の理由で完走しなかった。**

| 障害 | 原因 |
|---|---|
| 本番採点一覧の群が止まる | 本番が混在になったのに、10問すべてに文字を打つ作りのままだった |
| 採点一覧へ到達しない | 問が切り替わる一瞬どちらの操作部も居ないため、途中で降りていた |
| **作者の群が最初の1行で止まる** | `getByRole('button', { name: '作者' })` が「**作者名を確認する**」にも一致した |

**3つ目は062が追加した走査群そのものであり、一度も実行されていなかった。**
**構造として正しく書かれていることと、動くことは別である。**

したがって本発注では次を受入条件とする。

- **追加・変更した走査を実際に完走させ、その出力（件数と違反数の行）を報告に貼ること。**
  「追加した」だけでは受け付けない。
- **入口の名前で要素を探すときは厳密一致にすること。** 入口名は互いの部分文字列になりうる
  （`作者` ⊂ `作者名を確認する`、`歌本文` と `歌を確認する`）。
- **破壊試験を報告に含めること。** 発注062では3件とも未実施のまま報告が返り、検収者が実施した。
