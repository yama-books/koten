# ADR-0001: フロントエンド構成に Vite + TypeScript + Preact を採用する

- 状態: 採択
- 日付: 2026-08-30
- 決定者: 依頼者（裁定）／実装計画に基づく
- 関連: `docs/IMPLEMENTATION_PLAN.md` §3.1〜§3.3、確定事項 F-01、`docs/DESIGN_SYSTEM.md` の禁止事項、`docs/APP_SPEC.md` §4

## 文脈

古典学習帳（百人一首アプリ）は、GitHub Pages 上で静的配信する学習用 SPA として仕様化されている。実装計画 §3.1 は、正本 Markdown を読み取り専用の入力として `tools/build-data` がビルド前に生成物へ変換し、生成された静的アセットを SPA が同梱して配信する構成を前提にしている。

この前提のもとでフロントエンドの技術選定を行う必要があった。選定は次の制約に従わなければならない。

- 確定事項 F-01 がすでに「Vite + TypeScript + Preact」を採用フレームワークとして定めている（実装計画 §1.2 の確定事項一覧）。本 ADR は、その確定事項がどの理由で成立するか、実装計画 §3.2・§3.3 に基づいて記録し、以後の変更条件を明文化するものである。
- `docs/DESIGN_SYSTEM.md` は縦書き（`writing-mode`）と `prefers-reduced-motion` を CSS で直接扱うことを要求し、UI フレームワークの既定デザインとの衝突を禁止事項として挙げている。
- `docs/APP_SPEC.md` §4 は範囲 URL（`?from=&to=`）をアプリの主入口と定めている。

## 決定

- フロントエンドのビルドツールに Vite を採用する。
- 実装言語に TypeScript を採用する。
- UI ライブラリに Preact を採用し、スタイルは素の CSS（トークンは CSS 変数）で実装する。UI フレームワーク付属のコンポーネントライブラリやデフォルトテーマは採用しない。
- ルーティングは URL クエリのみで行い、ハッシュルーティング（`#/`）やパスベースの動的ルーティングは使わない。
- データ生成（Markdown の解析・正規化・検証・出力）はアプリの実行時ではなく、ビルド前工程（`tools/build-data`、Node/TS、ローカルおよび CI）に置く。アプリは生成済みの静的 JSON（`packages/{hyakunin,kanazukai}/src/data/generated/*.json`。ADR-0004 による構成）を読み込むだけとする。
- 公開対象ツリーを隔離し、内部資料や管理確認ページ（`tools/review-page/`）はこのツリーの外、または別の Vite エントリに置く。
  （本 ADR 起草時の想定は `app/` 単一ツリーだったが、ADR-0004 により `packages/{shared,hyakunin,kanazukai}` へ置き換わった。**隔離するという決定自体は変わらない。**）
- 統計送信は Firestore REST 直書き＋匿名アカウント使い捨てとし、Cloud Functions のようなサーバーサイド実行基盤は持たない（`shukudai-kanri` の実績構成を踏襲）。

## 却下した案

| 却下案 | 却下理由 |
|---|---|
| Next.js／SvelteKit 等のフルスタックフレームワーク | 確定事項 F-01 に反する。GitHub Pages での静的配信のみで要件が満たせ、サーバーサイドレンダリングやサーバーランタイムを要する構成は過剰である |
| 実行時に正本 Markdown をパースして表示する構成 | 正本が実行時依存になり、検証（V-01〜V-15 相当の整合性検査）のタイミングが公開後にずれる。ビルド前検証で止められたはずの不整合が、利用者の端末で初めて表面化する |
| 習熟度を数値カラムとして保存し、イベントごとに逐次更新する構成 | 規則版（`masteryRulesVersion`）を上げた際に過去イベントから再計算できず、複数端末の記録を統合する際に保存値を盲目的に上書きしてしまう |
| ハッシュルーティング（`#/`） | `docs/APP_SPEC.md` §4 が定める範囲 URL（`?from=10&to=20`）をクエリで指定する仕様と噛み合わず、共有された URL が読みにくくなる |
| PWA（オフライン対応・インストール可能化）の初回公開必須化 | `docs/APP_SPEC.md` §13 が「完全な PWA 化は初回公開後でもよい」としている。初回公開を遅らせる機能は段階実装へ回すという憲章の裁定優先順（8番目）に従い、任意項目に下げる |
| `shukudai-kanri` の「日単位使い捨て利用番号」をそのまま流用する構成 | `CONSTITUTION.md` §6 は「同じブラウザ保存領域で継続する無作為な利用番号」と、反復利用の集計を要求している。使い捨て番号では反復利用を数えられない。ガード手法（allowlist・サニタイズ・経路禁止）だけを流用し、番号の生存期間は継続方式に改める |
| 現リポジトリに remote を足してそのまま公開する構成 | 現リポジトリの履歴に許可未確認の原資料 PDF が含まれる（詳細は ADR-0003）。公開は新規履歴で行う |

## この決定が守るもの

- 確定事項 F-01（Vite + TypeScript + Preact）。
- `CONSTITUTION.md` §3（一次資料と生成物）: データ生成をビルド前工程に置くことで、正本を実行時にパースしない構造を保証する。
- `docs/DESIGN_SYSTEM.md` の禁止事項: 素の CSS 採用により、UI フレームワークの既定デザインと縦書き・モーション設定の衝突を避ける。
- `docs/APP_SPEC.md` §4: クエリベースのルーティングにより、範囲 URL を主入口とする仕様を GitHub Pages の base path 下でも 404 なく成立させる。
- 確定事項 F-04（Firebase は匿名統計と問題報告に限定、無料枠内が運用目標）。

## 変更条件

次のいずれかが観測されたら、この決定を見直す。

- GitHub Pages 以外のホスティング（サーバーサイド実行を要する環境）へ移行する必要が生じた場合。
- Preact のバンドルサイズまたは API 制約が、`docs/DESIGN_SYSTEM.md` の要求（縦書き・8 状態・レスポンシブ契約）を満たせなくなった場合。
- `docs/APP_SPEC.md` §4 の URL 仕様が変更され、クエリベース以外のルーティングが必要になった場合。
- PWA 化が初回公開の必須要件へ格上げされ、Service Worker 戦略が現行のビルド構成と両立しないことが判明した場合。

## 影響

- 実装計画 P1（最小実行基盤）の足場構築が本決定の構成に従う。
- 2 プロダクト構成（ADR-0004）では、本決定のディレクトリ構成（`app/` 単一ツリー）が `packages/{shared,hyakunin,kanazukai}` へ組み替えられる。技術選定（Vite + TypeScript + Preact、素の CSS、クエリルーティング）自体は変更されない。
