**統計はこれまで一度も届いていない。** 2026-09-06 のコンソール作業で判明した——
コンソールには全拒否ルール（`allow read, write: if false;`）しか入っておらず、
`stats_days_test` への `match` が無かった。同日リポジトリの規則を貼り付けて公開した。

これで2つのことが同時に起きた。

1. **ようやく届きうる状態になった。** ただし**まだ1件も届いたことは無い。誰も確かめていない。**
2. **書き込み口が開いた。** 現行の規則は `request.auth` も `request.app` も要求しない。
   **形さえ合えば誰でも書ける。** プロジェクトIDは公開ビルドに含まれ隠せない。
   全拒否だった間はこの口が閉じていた。**開いたのは 2026-09-06 である。**

**本発注は「届かせる」と「締める」を一続きで片付ける。** 途中で止めると、
**開いたまま放置**するか、**締めて届かなくする**かのどちらかになる。

## 1. 工程1：統計の入口一覧に「作者」を足す（旧・発注064）

### 1.1 直すこと

発注062が入口 `author` を新設したが、統計側は5つのままである。

| 場所 | 現状 |
|---|---|
| `packages/shared/src/telemetry/registry.ts` の `ENTRY_KEYS` | `['quick','view','learn','review','exam']`。**`author` が無い** |
| `packages/hyakunin/src/domain/stats.ts` の `entryCounts` | 同じ5つ。`session.entry in entryCounts` で弾く |
| `firebase/firestore.rules` | `hasAll` で同じ5つを要求し、**`size() == 5` で固定** |

**作者入口の利用は統計に1件も現れない。**「指導のために正確な集計を得たい」という目的に直接反する。

**発注062の落ち度ではない。** 062の準備書が「統計は対象外」と境界を引いたためで、
**境界の引き方を誤ったのは起草者（Sol役）である。**

### 1.2 順序（**外すと公開中の版から統計が書けなくなる**）

現行規則は `hasAll([5キー])` に加え `size() == 5` を課す。
**6キー必須へ差し替えると、いま公開されている版（5キーを送る）が全て拒否される。**

1. **規則を「5キーでも6キーでも通る」形にして配置する。** `size()` の固定をやめ、
   **`hasOnly([6キー])` かつ `hasAll([5キー])`** とする——知らないキーは拒み、`author` は在っても無くてもよい。
   **コンソール作業。リポジトリの `firebase/firestore.rules` も同時に更新する。**
2. **配置を確認してから**、`ENTRY_KEYS` と `domain/stats.ts` に `author` を足す。
3. **6キー必須へ締めるのは、公開版が入れ替わったあと。** 本発注では締めない（§5の後段で扱う）。

### 1.3 受入条件

- `ENTRY_KEYS` が6つになり、`isStatsPayload` が6キーの `entryCounts` を通す。
- **5キーの古い形も通ること。** 段階3が済むまで両方を受ける。
- **知らないキーを混ぜたものは拒むこと。** **拒否側の試験を必ず1本置く**——
  置かないと「緩めただけ」の変更が通ってしまう。
- `summarizeDailyStats` が作者入口の回を数え、**他の入口の数を変えない。**
- `firebase/firestore.rules` の更新分が**リポジトリにも入っていること。**
  **今回の重大な相違は、まさに配置とリポジトリが食い違っていたために起きた。**

## 2. 工程2：App Check のトークンを送る

### 2.1 裁定：**npm の依存を増やさない。REST で取る**

Firebase の App Check SDK を入れれば早いが、**採らない。**

- このリポジトリの実行時依存は **`preact` 1件だけ**である。新規依存の追加は Codex の領分ではない（D-68）。
- D-62 は App Check のプロバイダを選ぶ際、**「増えうる秘密の本数そのものを減らすのが最も確実な防御」**
  という理由で reCAPTCHA Enterprise を採った。**同じ理屈が依存にも当てはまる。**
- 必要な材料は既に `app-config.ts` にある——
  `appCheckSiteKey`・`appId`・`messagingSenderId`（＝プロジェクト番号）・`apiKey`。

**取り方**（**一次情報で裏を取ってから実装すること。ここに書いた理解を転記しない**）

1. reCAPTCHA Enterprise のスクリプトをサイトキー付きで読み込み、トークンを1つ得る。
2. そのトークンを **App Check の交換エンドポイント**へ渡し、App Check トークンを得る。
3. 得たトークンを `statsCreateRequest` の `appCheckToken` に渡す。**受け口は既にある**
   （`packages/shared/src/telemetry/transport.ts`。`null` ならヘッダを付けない）。

### 2.2 守ること

- **`packages/shared/src/telemetry/**` に送信もスクリプト読み込みも書かない。**
  W-10（telemetry に送信の語を出さない）と T-17（`transport.ts` は送信 API を呼ばない）を**外さない。**
  実装は `packages/hyakunin/src/telemetry/` 側に置く（`stats-sender.ts` と同じ層）。
- **`ui/` の下に置かない。** `tests/screen/no-pressure.test.tsx` が UI のソースに `fetch(` を許さない。
- **トークンが取れなくても学習を止めない。** 取得に失敗したら `appCheckToken: null` のまま送る。
  施行は入っていないので、それで届く。**例外を投げないこと。**
- **外部スクリプトを読み込む。** これは中学生を含む利用者の画面に第三者のスクリプトを載せることである。
  **読み込み先とサイトキーを `docs/HANDOFF.md` に記録すること。**

### 2.3 受入条件

- 同意していない利用者から**1件も出て行かない**こと（061の門を弱めない）。
  **リクエストが0件であることで見る。**「関数を呼んでいない」では不可。
- トークンが取れたとき **`X-Firebase-AppCheck` ヘッダが付き**、取れないとき**付かない**こと。**両方向で確かめる。**
- 取得に失敗しても `sendStats` が例外を投げず、送信自体は続くこと。
- 既存の静的検査（W-10・T-17・no-pressure）が**すべて緑のまま**であること。**免除一覧を増やさない。**

## 3. 工程3：**実際に1件届くことを確かめる**

**これが本発注の要である。** 規則も送信も揃ったが、**成功例が一度も無い。**

**確認は2人がかりになる。** 規則が `allow get, list, update, delete: if false;` を課しているため、
**書き込めても読み戻せない。** 実装者が自分だけで「届いた」ことを確かめる手段は無い。

**実装者がやること**

- 公開版または手元の `vite preview` から、**実際に `stats_days_test` へ1件書き込ませる。**
- **HTTPの状態コードと応答本文を、成功でも失敗でも報告に貼る。**
  `statsCreateRequest` の応答が **200 なら作成、409 なら既に同じ日の分がある**（どちらも到達の証拠）。
  それ以外は届いていない。**推測で原因を書かない。**
- **送信したドキュメントIDを報告に書く**（`clientNumber_localDate_product` の形）。
  依頼者がコンソールで探すために要る。
- **ネットワークへ出られない環境なら、そこで止めてSolへ戻すこと。** 到達を装わない。

**依頼者がやること**（実装者の報告を受けてから）

- コンソールで `stats_days_test` を開き、**報告されたドキュメントIDが実在することを確認する。**
- **これが済むまで工程3は完了ではない。** 実装者の報告だけで閉じない。

**手順の記録**：送信は「終わった日」だけを対象にする作り（`finishedDay`）で、当日は送らない。
確かめるには日付をまたぐか、保存された日次カウンタを前日の日付にして試すことになる。
**どうやって送らせたかを報告に残すこと。** 次に確かめる人が同じ手間をかけないためである。
