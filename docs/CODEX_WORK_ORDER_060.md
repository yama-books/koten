# 発注060準備書：全1200件の走査をどこで払うか

- 作成：2026-09-06、Opus 5。依頼者の起票指示による。
- 状態：**完了・クローズ（2026-09-06）。案Aを採用し、既存CIの全走査を維持する。コード変更なし。**
- 発端：依頼者から「全1200件の走査はなかなか重そうだが必須か。Luna や Sonnet に任せにくいか」との問い。**急ぎの案件ではない。発注059の完了後に検討する。**

## 1. 現状の事実

`npm run check:overflow` は5群で構成される。

| 群 | 件数 | 中身 |
|---|---|---|
| 閲覧 | **1200** | 100首 × 読み3表示 × 幅4種 |
| ホーム拡大 | 8 | 幅4 × 文字100/200% |
| 本番採点一覧 | 8 | 同上 |
| 057の新しい表示 | 16 | 同上 × 開示／紙△ |
| 出題画面（059 F-2 で追加） | 8 | 同上 |

- **1回およそ12分**（壁時計）。
- **モデルの消費はほぼ無い。** 起動1回と、終了後に要約数行を読むだけである。**週次資源を削っているのは走査ではなく、調査と発注書の読み書きである。** 問いの前提をここで訂正しておく。
- **毎回必須ではない。** `MIGRATION_LOG` §7.1 は「画面を直したときに走らせる」と条件付きである。ロジックや試験だけの変更なら要らない。
- 閲覧1200件が全首なのは抽出では足りないからである。**縦書きの崩れは歌ごとの中身に依存する**（句の長さ、漢字の密度、作者名の字数）。実例：058で73番の作者名を「権中納言匡房」→「前中納言匡房」へ変えた。**字数が変わる変更は、特定の1首だけで溢れうる。** 10首の抜き取りでは、その1首が入っていなければ何も証明しない。
- コードは `expectedCases = 1200` を持ち、**過不足とも「検査不全」として非0で終える。**

## 2. 委任について（結論：実行は任せてよい。設計と切り分けは任せない）

**走査の実行そのものは Luna・Sonnet に任せてよい。** build して1コマンド走らせ、最後の数行を読むだけであり、走査件数が合わなければ非0で止まるので黙って手を抜く余地がない。

**任せないのは前後の2つである。** 発注057〜059の実作業で、いずれもここで実際に間違えた。

1. **build し直さずに測った。** `vite preview` は `dist/` を配るので、直したはずのCSSを1度も見ずに全件緑になった。1回分を捨てた。
2. **新しい要素を1度も測っていない走査を書いた。** 掛詞の一言が出る問題に当たらないまま緑になっていたため、必ずそこへ辿り着く手順を足した。

**どちらも「緑が出た」だけでは気づけない。** 新しい検査条件の設計と、非0が出たときに本物の欠陥か意図した挙動かの切り分けは、画面を変えた本人が持つ。

## 3. 裁定結果（2026-09-06）

### 裁定1：走査を段階に分けるか — **案Aを採用**

| 案 | 内容 | risk |
|---|---|---|
| **A（起草者の推奨）** | 現状維持。「画面を直したとき」の条件を守り、分割しない | 変更なし。12分を払い続ける |
| B | 作業中は新表示の群だけ、**公開直前だけ全1200件** | **`expectedCases = 1200` を「常に全件」とする現行の設計を変える裁定が要る。** 分けた瞬間に「作業中の緑」が公開の証拠でなくなるため、公開手順に全件実行を必須として書き込むこと |
| C | 閲覧1200件を代表抽出へ縮める | **採らない見込み。** §1 の理由により、抽出は content 依存の欠陥を原理的に取り逃す。採るなら「どの首が代表か」を人が決めた根拠が要る |

現行手順はすでに「画面を直したとき」「統合後に1回」である。Bが省く反復は通常運用にはほぼ無く、分割コード・二種類の緑・公開手順への依存を増やす費用の方が大きい。したがって分割しない。Cは内容依存の欠陥を保証できないため採らない。

### 裁定2：CI の全走査を維持するか — **維持する**

調査の結果、`.github/workflows/ci.yml` はすでに `npm run build` → Chromium導入 → `npm run check:overflow` の順で全走査を実行していた。論点は「載せるか」ではなく「外すか」だった。CIのclean checkout後のbuildは古い `dist/` を測る事故を防ぐ独立証拠であり、手元実行は公開前、CIはpush後なので置き換えない。実行時間・ランナー費用の実害が計測されていない段階では外さない。

## 4. 着手する場合の受入条件

- 分割を採るなら、**`MIGRATION_LOG` §7 に「公開直前は全1200件」を明記**し、公開手順のチェック項目に入れること。
- **走査件数の門（過不足で非0）を弱めないこと。** 群を分けるなら群ごとに件数の門を持たせる。
- 既存の全群が違反0のままであること。
- 破壊試験：群を分けたあと、**分割後の「作業中の走査」だけを回して閲覧側の欠陥を仕込み、それが素通りすることを確認する**（＝分割の代償を実測して記録する）。素通りしないなら分割設計が間違っている。
- 上の破壊と同じ欠陥を**全件走査が赤として捕捉すること**も対で確認する。部分走査の素通りだけでは、全件側の検出力を証明しない。

## 5. 対象外

製品の画面・文言・判定・データ。本件は検査の運用だけを扱う。

## 6. クローズ（2026-09-06、Opus 5）

案Aのため**コードは1行も変えていない。** 本件で残すべきは運用規則だけであり、発注書に埋もれると次に読まれないので、下記を `HANDOFF.md` §4.1 へ移した。

- `check:overflow` は**毎回必須ではない**。画面または表示されるデータを変えたときに、統合後1回。

- **走査の実行は委任してよい。** 件数の門（過不足で非0）があるため手抜きが通らない。
- **新しい検査条件の設計と、非0が出たときの切り分けは委任しない。** 画面を変えた本人が持つ。

**再開の必要なし。** 分割を再検討するときだけ §3・§4 を読む。
