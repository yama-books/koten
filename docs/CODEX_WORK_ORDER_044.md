## 3. 裁定済み事項（**これに従う。決め直さない**）

### 裁定 1: 新規試験の名前は `Y-` で始める

043 が `X-` を使ったので次の記号にする。`Y-1` と `Y-2` の **2 本ちょうど**。
**種別を試験名のコメントに書くこと**（042・043 と同じ形式）。**2 本とも「弁別的」である。**

### 裁定 2: 複製そのものは、この発注では消さない

`registry.ts` が `isClientNumber` を import して複製リテラルを消す整理は、
**筋としては正しいが、この発注ではやらない。**

**理由**: 釘を打つ前に部材を動かすと、**穴が実在したことを後から証明できなくなる。**
**先に Y-1・Y-2 を刺し、複製を消すのはそのあとである**（親担当が `docs/HANDOFF.md` §8 へ「次にやること」として記録した）。

**親担当は、その整理が Y-1・Y-2 と衝突しないことを先に実測してある**——
`registry.ts` を `isClientNumber` に委譲する形へ書き換えると、**378/378 全緑・`typecheck` 0** だった（§5.1 の F-1）。
**Y-1 は正しい実装を赤にしない。**

### 裁定 3: Y-1 は `clientNumber` を、Y-2 は `expiresAt` を撃つ。混ぜない

**1 本が 1 つの穴に対応する。**
Y-1 に `expiresAt` の値を混ぜたり、Y-2 で `localDate` も一緒に見たりしないこと。
**混ぜると、どちらの制約が消えたのか破壊試験で切り分けられなくなる。**

### 裁定 4: 文字列でない値は Y-1 の担当ではない

`isStatsPayload` は `typeof value.clientNumber === 'string'` を**別の節で**見ている。
Y-1 に `undefined` や数値を混ぜると、**正規表現を潰す破壊で赤にならない値**が混ざり、
**Y-1 が「型検査も兼ねた曖昧な試験」になる。**
**Y-1 が置くのは、すべて文字列である**（下の表の 5 個）。
