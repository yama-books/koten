## 1. 工程1：復元カードを簡潔にし、バーを出す

### 1.1 いま何が起きているか（実機の画面より）

範囲 61〜75番（**15首。20首以下なので分割されていない**）で、次の3行が出ている。

```
範囲 61番〜75番・20首ずつに分けて全1回
いまは1回目（このまとまりはあと5首）・範囲全体であと5首
続きから始めると、この1回目のなかから10問を出題します。
```

**欠陥は2つ。**

1. **分割されていないのに分け方を説明している。** 「20首ずつに分けて全1回」は、
   まとまりが1つしかないとき**意味を持たない。**
2. **同じ数を2度言っている。** まとまりが1つなら「このまとまりはあと5首」と
   「範囲全体であと5首」は必ず一致する。

**これは発注058 R3 の設計不良である。**「分かりにくい」を直そうとして、
情報を足しすぎた。**起草者（Sol役）の責任である。**

### 1.2 裁定

- **まとまりが1つ（`chunkCount === 1`）のときは、分割に触れない。**
  「◯番〜◯番・あと◯首」だけにする。「20首ずつ」「全1回」「1回目」を出さない。
- **まとまりが2つ以上のときだけ**、いまの情報を出す。ただし
  **「このまとまりの残り」と「範囲全体の残り」が同じ数なら、片方だけにする。**
- **出題数の予告（「◯問を出題します」）は残す。** ここは重複していない。
- **進捗をバーで示す。** 範囲全体のうち何首を終えたかを見せる。

### 1.3 バーは既存の部品を使う

**`shukudai-kanri` から借りてこない。** このリポジトリに**すでにバーがある**——
`packages/shared/src/ui/components/MasteryMeter.tsx`。`role="meter"` と
`aria-valuenow`/`min`/`max` を持ち、320px・文字200%の走査も通っている。

**別プロジェクトの機構を持ち込むより、これを一般化する方が安い。**
`MasteryMeter` は「習熟度 ◯%」という文言を内側に持つので、
**文言を差し替えられる形へ広げるか、同じ CSS を使う薄い部品を1つ足す。**
**`MasteryMeter` の既存の使い方（結果画面・履歴）を壊さないこと。**

### 1.4 受入条件（工程1）

- **範囲が20首以下のとき**、復元カードに「20首ずつ」「全◯回」「◯回目」が**出ないこと。**
- **範囲が21首以上のとき**は出ること。**両方向で確かめる**——片方だけでは足りない。
- 2つの残り数が同じときに、**同じ数が2度出ないこと。**
- バーが `role="meter"` を持ち、`aria-valuenow` が残りではなく**進んだ量**を指すこと。
- **色だけで伝えないこと**（§5.2 の既存規則）。数字を併記する。
- 320px・文字200%で違反0。**復元カードの走査群を足す**（件数の門を付ける）。

## 2. 工程2：出題中の進捗バー

### 2.1 裁定

- 出題画面に**セッションの進捗バー**を出す。いまの `progressLabel`（「10番・3問目/10」）を置き換えず、**併記する。**
- **単位は「問」である。「首」ではない。** 依頼者の指摘は「あと〇首」だったが、
  **セッションの中で数えているのは問であり、1首から複数問出ることがある**（穴埋め5句＋作者）。
  **首で数えると、5問答えて1首しか減らない画面になり、かえって進まなく見える。**
  復元カードは「首」、出題中は「問」で使い分ける。
- **本番でも出す。** 本番は解答中に正誤を出さない規則だが、**進捗は正誤ではない。**

### 2.2 受入条件（工程2）

- 練習・作者・本番・再確認の**4つとも**バーが出ること（1つ代表では足りない）。
- 最初の問で0%、最後の問を終えたときに100%になること。**両端を確かめる。**
- **本番の解答中に正誤が出ないことを弱めないこと**（056 F-1・F-2）。
- 320px・文字200%で違反0。**出題画面の走査群は既にある**ので、そこで見る。

## 3. 工程3：ホーム画面への追加の案内

### 3.1 いま分かっていること（調査済み）

- **`manifest` が無い。** `packages/hyakunin/public/` にあるのは `404.html`・アイコン・フォントだけで、
  `index.html` からの参照も無い。
  **iOS/iPad は `apple-touch-icon` だけで「ホーム画面に追加」ができる**（アイコンは配置済み）が、
  **Android Chrome の追加体験には `manifest` が要る。**
- **「ホームから起動したときに消せるか」→ できる。**
  `window.matchMedia('(display-mode: standalone)')` と、iOS Safari の `navigator.standalone` で判る。
  **両方を見ること。** iOS は `display-mode` を返さない場合がある。

### 3.2 裁定

- **ホーム画面から起動しているときは、案内を一切出さない。** 追加済みの人に追加を勧めない。
- **初回だけ目立つ案内を出す。** ただし**ダイアログにしない。タイトルより上に出さない。**
  059・058で同じ失敗を繰り返している。**画面下部に、閉じられる1枚**とする。
- **2回目以降は、いまと同じ静かな最下部の1行**に落とす。
- **閉じたことを覚える。** 置き場は**端末内の保存（`localStorage`）**とし、
  **`UserSettings` に項目を足さない。** 学習記録ではなく端末ごとの見た目の設定であり、
  設定に足すと書き出し・取り込み・統計へ波及する（MVP④・061）。
- **iOS と Android で文面を変える。** iOS は手順を示すしかない（共有 → ホーム画面に追加）。
  Android は `beforeinstallprompt` が使えるなら**ボタン1つ**にしてよい。
  **使えない環境で壊れないこと。**
- **`manifest` を足すかは実装者の判断でよい。** 足すなら**アイコン・名前・`display`・`start_url` だけ**の
  最小構成とし、`start_url` は `/100/` を指すこと（`base` と食い違わせない）。

### 3.3 受入条件（工程3）

- **ホーム画面から起動したとき、案内が出ないこと。** 通常のブラウザでは出ること。**両方向で確かめる。**
- 閉じたあと、**再読み込みしても出ないこと。**
- **案内がタイトルより後ろに出ること**（058・059で指摘された点）。
- **案内を閉じられること。** 閉じる手段の無い案内を作らない。
- **保存が使えない環境（プライベートウィンドウ等）で壊れないこと。** 出続けてもよいが、例外を投げない。
- 320px・文字200%で違反0。**案内を出した状態で測ること**——出していない状態で測っても何も証明しない。
