## 0. なぜこれを出すか

`RELEASE_READINESS` §2 の **G-3**：**`review/readings.yaml` は100首とも `pending`。承認経路が一度も動いていない。**

実測（2026-09-06）——`review/` の5台帳のうち、

| 台帳 | `pending` の行 |
|---|---|
| `authors.yaml` | 1（見出しの説明のみ） |
| `blanks.yaml` | 1（同上） |
| **`readings.yaml`** | **101** |
| **`kugire.yaml`** | **101** |

**3つの台帳が、100首すべて未承認のままである。**
ところが生成データ `poems.json` は **`reading.status: "confirmed"`** と書いている（64番で確認済み）。

**台帳は「人が書き込む唯一の場所」と自ら宣言している**（`readings.yaml` 1行目）。
その台帳が未承認なのに、成果物が「確認済み」と名乗っている。**どちらかが嘘である。**

**これは、このプロジェクトで繰り返し出ている型そのものである**——
**仕組みはあるが一度も動いておらず、それでも緑に見える。**
（065 の「規則がコンソールに置かれていなかった」、066 の「学年が集まらない」と同じ型である。）

## 2. 想定される結末は2つある（**どちらでも工程1の報告で止まる**）

### (A) 台帳の `status` が生成データに効かない場合

**台帳は飾りである。** `pending` のままでも `confirmed` と出る。
**この場合、直すべきは台帳ではなく「名乗り」である**——
承認されていないものを「確認済み」と表示している。

### (B) 台帳の `status` が効く場合

**では、なぜ100首とも `pending` なのに `confirmed` と出るのか。**
別の既定値が上書きしている可能性が高い。**その上書きの場所を突き止めること。**

**どちらであっても、直し方の裁定は Sol が行う。** 工程1の報告で**必ず止まること。**
**「ついでに直す」ことをしないこと。** これは正本の確からしさに関わる。
