## 1. 背景

変体仮名メーカーは NINJAL「学術情報交換用変体仮名」を扱う学習アプリ。
2026-09-23 に公式Unicode字体265件 ＋ 公式外1件（`U+1B10C`）の **266件** を公開した（PR #27）。

件数が増えたため、**見た目で区別できない字が同じ4択に並ぶ** 危険が出てきた。
監査文書 `NINJAL_GLYPH_AUDIT_2026-09-20.md` §4.3〜§4.4 に具体例がある。

| 符号位置 | 公式の割当 | 実際の形 |
| --- | --- | --- |
| `U+1B052` | せ / 世 | 現代の「を」そっくり |
| `U+1B11A` | を / 越 | 「戈」状。現代の「せ」に見えなくもない |
| `U+1B11B` | を / 遠 | 現代の「を」に最も近い |
| `U+1B11C` | を / 遠 | 「と」に近い崩し |

### どこで問題になるか

字形そのものを選ばせる4択は **字母逆引き**（`reverseJiboChoices()`）だけ。
この4択は音価（読み）を横断して選択肢を取り、**標準ひらがな（あ〜ん の48字。ゐ・ゑ を含む）も選択肢に混ぜる**。

したがって表には次の2種類が要る。

1. 変体仮名 × 変体仮名（例: `U+1B052` せ／世 と `U+1B11B` を／遠）
2. 変体仮名 × 標準ひらがな（例: `U+1B052` せ／世 と 標準の「を」）

**同じ読み（`kana`）どうしの組は表に入れない。** 出題は読みが違えば別答になるので、
同じ読みの中で似ていても4択の正誤は揺れない。
**同じ字母（`jibo`）どうしの組も入れない。** 字母逆引きでは同じ字母の字は現在すでに選択肢から外している。

## 2. 作るもの

### 2.1 `vintage-kana/data/glyph-confusion-pairs.json`（新規）

```jsonc
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-2X",
  "method": "（下記 §3 のどの方法で作ったかを1〜2文で）",
  "universe": {
    "hentaigana": 266,      // ui-glyph-master.json の件数
    "standardHiragana": 48  // あ〜ん（ゐ・ゑ を含む48字）
  },
  "pairs": [
    {
      "a": "U+1B052",          // 変体仮名は glyph_id、標準ひらがなは "std:を" の形
      "b": "std:を",
      "kind": "hentaigana-standard",   // または "hentaigana-hentaigana"
      "evidence": "audit",             // 下記
      "score": null,                   // 画像比較をした場合の類似度（0〜1）。していなければ null
      "note": "崩した「世」が現代の「を」とほぼ同形（監査 §4.3）"
    }
  ]
}
```

規則:

- `a` と `b` は **正規化した順序**で持つ（JavaScript の `a < b` による文字列比較。`"U+…" < "std:…"` なので、変体仮名と標準ひらがなの組では常に `a` が変体仮名・`b` が `std:` になる）。
  同じ組を2回書かない。自分自身との組を書かない。
- 変体仮名の識別子は `ui-glyph-master.json` の `glyph_id`（`U+1B0xx` 形式）。
  **266件の中に存在する `glyph_id` だけ**を使う。
- 標準ひらがなは `std:` ＋ 1文字。`あ〜ん` の48字（`index.html` の `KANA_ORDER` と同じ。ゐ・ゑ を含む）だけ。
- 同じ `kana` どうし・同じ `jibo` どうしの組は入れない（§1）。
  標準ひらがなの `jibo` は `index.html` の `STANDARD_HIRAGANA_JIBO`（読むだけ）に従う。
- `evidence` は次のいずれか。
  - `"audit"` — 監査文書に明記されている組
  - `"render"` — §3.2 の画像比較で機械的に見つけ、目視でも似ていると確認した組
  - `"render-unreviewed"` — 画像比較で閾値を超えたが、目視確認していない組

### 2.2 `tests/unit/vintage-kana-confusion-pairs.test.ts`（新規）

`node:test` と `node:assert/strict` で書く（`tests/unit/ninjal-glyph-catalog.test.ts` と同じ流儀）。
最低限、次を固定する。

1. `pairs` の全 `a` / `b` が、`ui-glyph-master.json` の `glyph_id` か `std:` ＋ 48字のどれかである
2. 自分自身との組が無い。同じ組の重複が無い（順序違いも重複とみなす）
3. `a < b` の順序規則を全件が守っている
4. 同じ `kana` どうし・同じ `jibo` どうしの組が無い
5. `kind` が `a` / `b` の種類と矛盾しない
6. `evidence` が3種のどれか。`score` は `null` か 0〜1
7. **監査で確定している組が必ず入っている**（下の §3.1 の表）
8. `universe.hentaigana` が `ui-glyph-master.json` の実件数と一致する

## 3. 作り方

### 3.1 監査で確定している組（必ず入れる。`evidence: "audit"`）

| a | b | 根拠 |
| --- | --- | --- |
| `U+1B052`（せ／世） | `std:を` | 崩した「世」が現代の「を」とほぼ同形 |
| `U+1B052`（せ／世） | `U+1B11B`（を／遠） | 同上。`U+1B11B` は現代の「を」に最も近い |
| `U+1B11A`（を／越） | `std:せ` | 「戈」状で現代の「せ」に見える |

`a < b` の順序規則に合わせて並べ直すこと（上の表は読みやすさ優先で書いてある）。

### 3.2 画像比較で候補を広げる（可能なら）

あなたの実行環境で次ができる場合に限り行う。**できなければ 3.1 だけで提出してよい**（その旨を `method` に書く）。

1. `Noto Serif Hentaigana`（SIL OFL 1.1）を Google Fonts から取得する。
   取得できない・通信できない環境なら、この節は丸ごと飛ばす。**別のフォントで代用しない**
   （アプリが実際に描く形と違う形で比較しても意味がない）。
2. 標準ひらがな48字は、アプリの実表示と同じく **Klee One** で描く（取得できなければ標準ひらがなとの比較は飛ばす）。
3. 266字 ＋ 48字を同じ寸法（例: 64px 四方、字面を中央寄せ・字面の外接矩形で正規化）で描き、二値化する。
4. §1 の除外（同じ `kana`・同じ `jibo`）を適用したうえで、全組の類似度（IoU など。方法を `method` に書く）を計算する。
5. 上位から見て、**§3.1 の3組がどの順位に来るか** を報告に書く。
   この3組が上位に来ない尺度なら、その尺度は人の見え方と合っていないので使わない。
6. 閾値を超えた組を `render-unreviewed` で入れる。**多くても40組まで**。
   目視で似ていると確認できたものだけ `render` に上げる。

`score` には 4 で計算した値を入れる。

**フォントファイルそのものはリポジトリにコミットしない。** 比較用スクリプトを残す場合は
`tools/vintage-kana-confusion/` 以下に置き、フォントは実行時に取得する形にする。
CI からは呼ばない（外部通信を伴うため。NINJAL監査の `--fetch` と同じ扱い）。

## 4. 確認とコミット

```
npm ci
node --experimental-strip-types --test "tests/unit/vintage-kana-confusion-pairs.test.ts"
npm run test:node
```

`npm run check:vintage-kana` は Playwright とブラウザを使うので、実行できる環境なら回す。
できなければ「未実行」と報告に書けばよい（`index.html` を触っていないので結果は変わらない想定）。

コミットは次の単位に分ける。

1. `glyph-confusion-pairs.json` とテスト
2. （3.2 を行った場合）比較スクリプト

コミットメッセージは既存に合わせて `feat(vintage-kana): …` / `test(vintage-kana): …` の形。
`vintage-kana-main` へ push する。push 前に `git pull --ff-only origin vintage-kana-main` で
ローカル側の変更を取り込むこと。**コンフリクトが出たら解消せず止めて報告する。**

## 5. 報告に書くこと

- 最終的な組数（`evidence` 別の内訳）
- 3.2 を行ったか。行った場合は尺度・閾値・§3.1 の3組の順位
- 3.2 を行わなかった場合は、その理由（通信不可・フォント取得不可 など）
- 実行したテストと結果。実行できなかったものがあればその名前
- 表を作る途中で気づいた、`ui-glyph-master.json` 側の疑わしい点（直さずに報告だけ）

## 6. この作業のあとローカル側でやること（参考・あなたは実施しない）

1. 表を独立に検証する（件数・順序規則・3.1 の3組）。
2. `reverseJiboChoices()` に組み込む。
   - 低習熟: 混同ペアを誤答候補から **除外**
   - 高習熟: 混同ペアを誤答候補に **優先して並べる**（見分けの訓練にする）
3. 字の解説ダイアログ（`glyphInfoDialog`）に「形が似ている字」として出す。
4. 字母逆引きを複数正解に対応させる。
