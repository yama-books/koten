## 0. 何をしたか

国立国語研究所「学術情報交換用変体仮名」公開一覧を全件取得して
`vintage-kana/data/ninjal-glyph-catalog.json` に正本として保存し、
現行UIキャッシュ138字と全件突合した。あわせて「せ」と「を」に同じ字が見える件を、
データ・フォント・レンダリングの各層で切り分けた。

取得方法は `tools/ninjal-catalog/index.mjs` に実装した。一覧ページは Next.js の静的生成で、

## 3. 誤分類・不一致の詳細

いずれも Unicode Character Database の文字名で裏を取った。

### 3.1 `U+1B0D8` — 仮名と字母の両方が誤り（要修正）

| | 仮名 | 字母 |
| --- | --- | --- |
| 現行 `ui-glyph-master.json` / `FALLBACK_GLYPHS` | **る** | **留** |
| NINJAL公式（`350020010`） | **も** | **毛** |
| UCD文字名 | `HENTAIGANA LETTER MO-2` | |

公式とUnicode正典の両方が「も／毛」で一致しており、現行データが誤っている。
`totalObserved: 2 / witnessCount: 1` と出現は少ないが、**学習者に誤った読みを教える**ため優先度は高い。
「る」の現行7件が公式6件を超えていたのはこれが原因で、修正すると6件に収まる。

### 3.2 `U+1B0E6` — 字母が誤り（要修正）

| | 仮名 | 字母 |
| --- | --- | --- |
| 現行 | ゆ | **由** |
| NINJAL公式（`370030010`） | ゆ | **遊** |
| UCD文字名 | `HENTAIGANA LETTER YU-4` | |

仮名は正しい。公式の「ゆ」は `U+1B0E4`（由）・`U+1B0E5`（由）・`U+1B0E6`（遊）の3件で、
現行は3件目の字母を「由」と取り違えている。
字母クイズ（逆引き）で誤答判定を生むので修正が必要。

### 3.3 `U+1B10C` — 公式一覧に存在しない（要判断、削除は非推奨）

現行は「わ／王」として収録（`totalObserved: 353 / witnessCount: 12` と高頻度）。
Unicodeには `HENTAIGANA LETTER WA-5` として実在するが、**NINJAL公式一覧には掲載が無い**。
公式の「わ」は `U+1B108`（倭）・`U+1B109`（和）・`U+1B10A`（和）・`U+1B10B`（王）の4件である。

これは「現行データの誤り」ではなく、**学術情報交換用セットの選定範囲と、Unicodeの符号化範囲のずれ**である。
実資料で353回観測されている以上、消すと観測事実の方を捨てることになる。
`inOfficialCatalog: false` の印を付けて残すことを推奨する（§7）。

## 4. `U+1B11C` 重点監査 —「せ」と「を」に同じ字が見える件

結論を先に書く。

> **データ・フォント・レンダリングのいずれにも欠陥は無い。**
> `U+1B052`（せ／世）と `U+1B11C`（を／遠）の **字形そのものが、実際によく似ている**。
> これは公式資料どおりの正しい表示であり、バグではない。UIの出題設計の問題である。

### 4.1 公式一次資料の確認

| 項目 | 値 |
| --- | --- |
| ninjal_id | `470050020` |
| 平仮名 | **を** |
| 字母 | **遠** |
| Unicode | **U+1B11C** |
| 文字 | **𛄜** |
| MJ文字図形名 | `MJ090297` |
| UCD文字名 | `HENTAIGANA LETTER WO-7` |

指令書の記載どおりであることを、一次資料とUnicode正典の双方で確認した。

### 4.2 層ごとの切り分け

| 層 | 検査方法 | 結果 |
| --- | --- | --- |
| **公式データ** | 「せ」5行と「を」7行の符号位置集合の積を取る | **交わり0**。せ = U+1B052/1B053/1B055/1B056（＋瀬はUnicode未付与）、を = U+1B116〜U+1B11C |
| **現行 `ui-glyph-master.json`** | 同上 ＋ `character` と符号位置の一致検査 | **混同なし**。せ = U+1B052・U+1B055、を = U+1B11A・U+1B11C |
| **`index.html` の `FALLBACK_GLYPHS`** | 埋め込み配列と `ui-glyph-master.json` を照合 | **完全一致**。フォールバック経路でも取り違えは起きない |
| **Webフォントのcmap** | Google Fonts `Noto Serif Hentaigana` v17 の kana-extended サブセット woff2 を展開しcmapを解析 | 294符号位置 → **294個の異なるグリフID**。重複割当ゼロ。U+1B052=gid81、U+1B11C=gid283 |
| **フォントの被覆** | `unicode-range: U+1B000-1B122` とcmap実体 | 公式265文字を **全部含む**。fallbackに落ちる文字は無い |
| **実レンダリング** | 実ブラウザのcanvasに公式265文字を64px四方で描画し、アルファ値をビット化して比較 | **265文字 → 265通りの異なるビットマップ**。空白描画0件、同一描画0件 |

つまり、符号位置 → グリフ → 画素のどこを見ても取り違えは起きていない。

### 4.3 では何が起きているか

`U+1B052`（せ／世）の字形は、崩した「世」が **現代の「を」とほぼ同じ形** になる。
`U+1B11C`（を／遠）は現代の「を」の直接の祖先なので、当然「を」の形をしている。
結果として、**別字だが見た目がほとんど同じ** という状態が正しく表示されている。
`U+1B11B`（を／遠）も同系統の形で、3つ巴になっている。

実機で「せ」と「を」に同じ字が見えたという報告は、**表示の不具合ではなく観察として正しい**。

### 4.4 UI側に必要な対応（実装はしていない）

`index.html` は今回触っていない。必要な修正案は以下。

1. **4択の選択肢生成で、`U+1B052` と `U+1B11C`/`U+1B11B` を同一問題に同時に出さない。**
   見た目で判別できない選択肢を並べると、正答が運になる。
   現行は `focusedReadingPool` / `focusedJiboPool` が同音価内から誤答を取るため同時には出ないが、
   公式全件を投入して音価横断で誤答を引くようにすると、この組が衝突しうる。
   **「見た目が近い字」の除外リスト、または混同許容ペアの表** を先に用意すること。
2. **字形が似ている旨を、字の解説（`glyphInfoDialog`）に出す。**
   「この字は『を』とよく似た形だが、字母は『世』で読みは『せ』」と書けば、
   学習者の疑問がそのまま学習材料になる。
3. **自由入力の採点で、混同ペアを「惜しい」扱いにする。**
   現行は `FREE_INPUT_INCORRECT_DECREMENT=5` で習熟度を下げる。
   字形が事実上同じものを誤答として減点するのは、学習者にとって理不尽である。

混同ペアの根拠データは、本監査のレンダリング比較と同じ手順で機械的に作れる（§6）。

国立国語研究所サイトポリシー（https://www.ninjal.ac.jp/utility/policy/）:

- サイトのコンテンツの著作権は、特に断りの無い限り国立国語研究所に帰属する。
- 印刷媒体・CD-ROM・VTR・放送等で利用する場合は **事前連絡が必要**。
- リンクは自由。

Webアプリへの画像の複製・再配布については明示が無く、**「断りの無い限り著作権はNINJAL」の原則が効く**。
公開アプリへ同梱する場合は事前の許諾確認が要る、と判断した。

### 5.4 表示方法の分類と推奨

| 群 | 件数 | 表示手段 |
| --- | --- | --- |
| **Unicodeテキストで表示できる**（`renderability: "unicode-text"`） | **265** | `Noto Serif Hentaigana` で全件描画可能。実測で確認済（§4.2） |
| **別の表示手段が必要**（`renderability: "non-unicode"`） | **28** | Unicode符号位置が無いため文字として描けない |

28件について、安全な順に:

1. **当面はカタログに載せるが、UIには出さない。**
   一覧・学習・出題のいずれからも除外し、`renderability` で機械的に弾く。
   データとしては保持するので「公式に存在するのに取りこぼした」状態にはならない。
2. **一覧画面にだけ、字形を伴わない行として出す。**
   「字母：得（Unicode未付与・字形は公式サイト参照）」と表示し、`source_url` へリンクする。
   リンクはポリシー上自由なので、許諾なしで実施できる。**これを推奨する。**
3. 画像を同梱したい場合は、**先に国立国語研究所へ利用許諾を照会する。**
   許諾が取れるまで `public/` 以下に画像を置かない。
   `THIRD_PARTY_NOTICES.md` への追記も許諾後に行う。

**絶対にやってはいけないこと**: 28件のUnicode欄が空だからといってカタログから落とすこと。
落とすと公式293件の監査可能性そのものが失われる。

## 6. 再現手順


`--fetch` / `--verify` は外部サイトに触るため **CIには入れていない**。

自動テスト（`tests/unit/ninjal-glyph-catalog.test.ts`、11件）が固定している契約:

- `ninjal_id` 全件ユニーク
- Unicode符号位置・Unicode文字の重複なし

- Unicode未付与行を文字化していない（`unicode`/`code_point`/`character`/`mj_glyph_name` がすべて `null`）

## 7. UI統合の推奨データ構造

### 7.1 やってはいけない統合

公式293件を現行 `GLYPHS` にそのまま流し込むと、次が同時に壊れる。

- 「書いてみる」のおまかせ生成が、実資料で観測された138字から公式全字体へ広がる。
  観測0回の字体が混ざり、**実在しない字面の文章が生成される**。
- 出題プールが138→265に膨らみ、習熟度の設計（`CHOICE_MASTERY_CAP` 等）が想定する母数から外れる。
- Unicode未付与28件が文字として描けず、空白または豆腐になる。
- `U+1B10C`（わ／王、観測353回）が公式一覧に無いため、単純置換だと **消える**。

### 7.2 推奨する3層構造

```
layer 1: official catalog   data/ninjal-glyph-catalog.json   293件（公式の正本・頻度を持たない）
layer 2: observed corpus    data/glyph-distribution*.json    実資料の出現分布（頻度の正本）
layer 3: ui cache           data/ui-glyph-master.json        両者を結合した派生キャッシュ
```

layer 3 を、現在の138件から「公式265件 ＋ 公式外の観測字体」へ広げ、各行に出自の印を付ける。

```jsonc
{
  "kana": "を",
  "glyph_id": "U+1B11C",
  "character": "𛄜",
  "jibo": "遠",
  "ninjal_id": "470050020",      // 公式カタログへの参照。公式外なら null
  "inOfficialCatalog": true,     // NINJAL学術情報交換用セットに載っているか
  "renderability": "unicode-text",
  "totalObserved": 3538,         // layer 2 由来。未観測なら 0
  "witnessCount": 15,
  "observed": true               // totalObserved > 0 の別名。プール選択はこれで切る
}
```

`U+1B10C` は `inOfficialCatalog: false` / `observed: true` になり、消えずに残る。
Unicode未付与28件は `renderability: "non-unicode"` / `observed: false` になる。

### 7.3 機能ごとの母集団

| 機能 | 使う集合 | 理由 |
| --- | --- | --- |
| **「書いてみる」おまかせ生成** | `observed === true` **のみ**（現行138字相当） | 現在の挙動を変えない。実在した字面だけを出す |
| 「書いてみる」手動選択 | `renderability === "unicode-text"` の全件 | 使いたい字を選べる自由は広げてよい |
| 一覧 | 全293件 | 公式の全体像を見せる。未付与28件は §5.4 案2 |
| クイズ出題 | `observed === true` | 習熟度設計の母数を現行のまま保つ |
| クイズの誤答候補 | `observed === true` かつ **混同ペア除外** | §4.4-1 |
| 字母逆引き | 同一字母に複数字体があるため **複数正解を許す** | §2「同一字母に複数字体」50組 |
| 字の解説 | 全293件（`notes`・`mj_glyph_name`・`source_url` を表示） | 公式備考が学習材料になる |

**`observed` フラグをおまかせ生成の唯一の入口にすれば、公式全件を入れても現行の生成挙動は変わらない。**
これが今回いちばん重要な設計条件である。

## 8. UI担当が次にやること

優先順に並べた。1〜3はデータ修正のみで、UI構造に触らない。

1. **`U+1B0D8` を「る／留」から「も／毛」へ直す。**（§3.1）
   `data/ui-glyph-master.json` と `index.html` の `FALLBACK_GLYPHS` の両方。
   誤った読みを教えている唯一の行なので最優先。
   直したら `tests/unit/ninjal-glyph-catalog.test.ts` の「既知の不一致」期待値も更新する。
2. **`U+1B0E6` の字母を「由」から「遊」へ直す。**（§3.2）同上。
3. **`U+1B10C` に `inOfficialCatalog: false` を付ける。**（§3.3）削除はしない。
4. **layer 3 のスキーマを §7.2 へ拡張し、`observed` フラグを導入する。**
   この段階では件数を増やさず、現行138字に印を付けるだけにする。挙動が変わらないことを先に確認する。
5. **おまかせ生成・クイズ出題の母集団を `observed === true` に固定する。**
   ここまで済ませてから、はじめて公式265件を layer 3 へ投入する。順序を逆にしない。
6. **混同ペア表を作り、4択の誤答候補から除外する。**（§4.4）
   `U+1B052` × `U+1B11C`/`U+1B11B` が既知。全件のレンダリング比較で機械的に洗い出せる。
7. **字母逆引きの単答契約を複数正解へ広げる。**（§2）
   `tests/unit/vintage-kana-rc25.test.ts` の逆引き契約も一緒に更新が要る。
8. **Unicode未付与28件の一覧表示を §5.4 案2 で実装する。** 画像は同梱しない。
